    TicketSource¶

    Das TicketSource-Protocol ist die Abstraktionsgrenze zur Quellsystem-Welt. Heute existieren Implementierungen für GitHub und GitLab; weitere Quellen (Jira, ServiceNow, …) implementieren dasselbe Protocol.

    Protocol¶

    protocol TicketSource: Sendable {
    /// Ein Polling-Durchlauf. Liefert Tickets, die zur Verarbeitung bereit sind —
    /// gefiltert nach Trigger-Modus (Fresh-Issues bzw. Revise-PRs) und mit
    /// gesetztem `Ticket.trigger`.
    func pollOnce() async throws -> [Ticket]
}

    Heutige Implementierungen¶

    GitHubSingleRepoSource¶

    Pollt ein Repo via zwei Endpoints:

    • GET /repos/<repo>/issues?labels=<triggerLabel> für frische Tasks
    • GET /repos/<repo>/issues?labels=<reviseLabel> für Revise-PRs (wenn reviseEnabled)

    Beide Calls nutzen separate ETag-Dateien, sodass 304-Antworten weiterhin keine Rate-Limit-Quota verbrauchen. Pro entdecktem Revise-PR macht der Daemon einen zusätzlichen GET /repos/<repo>/pulls/<n>-Call (via PullRequestLookup), um Head- und Base-Branch zu ermitteln.

    GitHubMultiRepoSource¶

    Wrappt N GitHubSingleRepoSource. Pollt seriell pro Repo. Fehler in einem Repo blockieren die anderen nicht (werden geloggt, Loop läuft weiter).

    GitHubOwnerScopeSource¶

    Nutzt GitHub-Search-API mit zwei Queries:

    • is:issue is:open label:"<triggerLabel>" user:<owner> für Fresh
    • is:pr is:open label:"<reviseLabel>" user:<owner> für Revise

    Ein einziger Call pro Trigger-Modus findet alle Tickets über alle Repos eines Accounts/Org.

    Search-API-Rate-Limit

    30 Calls/min — bei pollInterval: 5 und aktivem Revise-Modus sind das 24 Calls/min. Knapp unter dem Limit, aber tunable über pollInterval.

    GitLabSingleProjectSource¶

    Pollt ein GitLab-Projekt mit zwei Endpoints pro Tick:

    • GET /api/v4/projects/<encoded>/issues?labels=<triggerLabel>&state=opened für Fresh-Tickets.
    • GET /api/v4/projects/<encoded>/merge_requests?labels=<reviseLabel>&state=opened für Revise-Tickets (nur wenn reviseEnabled). MR-Listings liefern source_branch/target_branch bereits mit — kein extra Lookup nötig.

    URL-encoded Path erlaubt mehrstufige Pfade (group/subgroup/project). Auth via PRIVATE-TOKEN-Header (anders als GitHub, das Authorization: Bearer nutzt).

    GitLabMultiProjectSource¶

    Wrappt N GitLabSingleProjectSource — pendant zu GitHubMultiRepoSource. Fehler in einem Projekt blockieren die anderen nicht.

    GitLabGroupScopeSource¶

    Pollt eine ganze GitLab-Gruppe (inkl. Subgruppen) via GET /api/v4/groups/<encoded>/{issues,merge_requests}. Der Projekt-Pfad pro Treffer kommt aus references.full (group/project#42 bzw. group/project!42). group darf hierarchisch sein (group/subgroup) und wird URL-encoded.

    Factory + Konfiguration¶

    TicketSourceFactory hat zwei Einstiegspunkte, je nach config.provider:

    // provider == "github"
let source = TicketSourceFactory.makeGitHub(client: githubClient, config: config)

// provider == "gitlab"
let source = TicketSourceFactory.makeGitLab(client: gitlabClient, config: config)

    Das eigentliche Wiring sitzt in App.swift und schaltet auf config.provider um.

    provider WatchTarget gewählte Source
    github .repo("owner/name") GitHubSingleRepoSource
    github .repos([…]) GitHubMultiRepoSource
    github .ownerScope("owner") GitHubOwnerScopeSource
    gitlab .repo("group/project") oder .repo("group/sub/project") GitLabSingleProjectSource
    gitlab .repos([...]) GitLabMultiProjectSource
    gitlab .ownerScope("group") oder .ownerScope("group/sub") GitLabGroupScopeSource

    Filter¶

    TicketFilter.ready(_ tickets:, kind:) macht den finalen Schliff vor Übergabe an die Pipeline. Filterregeln hängen vom PollKind ab:

    Kind Erwartet Wird gefiltert
    .freshIssue Issue (kein PR) mit Trigger-Label agent:in-progress, agent:done, agent:failed, alle PRs
    .revisePR Pull/Merge Request mit Revise-Label agent:revising

    agent:revised und agent:revise-failed blocken die Revise-Pipeline nicht — sie zeigen nur den Status der vorigen Iteration. Setzt der Reviewer agent-revise erneut, beginnt eine neue Iteration. Ohne erneutes Setzen verlässt das Polling den PR ohnehin (das Trigger-Label fehlt).

    ETag-Persistenz¶

    Pro Source-Endpoint eine ETag-Datei:

    Source ETag-Pfad
    GitHubSingleRepoSource(repo: "owner/name") Fresh ~/.agentry/etags/owner-name.etag
    GitHubSingleRepoSource(repo: "owner/name") Revise ~/.agentry/etags/owner-name-revise.etag
    GitHubOwnerScopeSource(owner: "x") Fresh ~/.agentry/etags/owner-x.etag
    GitHubOwnerScopeSource(owner: "x") Revise ~/.agentry/etags/owner-x-revise.etag
    GitLabSingleProjectSource(project: "g/p") Fresh ~/.agentry/etags/gitlab-g-p.etag
    GitLabSingleProjectSource(project: "g/p") Revise ~/.agentry/etags/gitlab-g-p-revise.etag
    GitLabGroupScopeSource(group: "g") Fresh ~/.agentry/etags/gitlab-group-g.etag
    GitLabGroupScopeSource(group: "g") Revise ~/.agentry/etags/gitlab-group-g-revise.etag

    Implementierung: ETagStore.swift.
