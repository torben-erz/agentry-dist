    Agentry¶

    Plattform-agnostisches Agenten-Framework. Ein wartender Daemon empfängt Trigger (Tickets aus GitHub oder GitLab), übergibt sie an einen AI-Agent (Claude Code oder OpenAI Codex) zur autonomen Bearbeitung und meldet das Ergebnis als Pull/Merge Request zurück.

    flowchart LR
    A[Ticket-Quelle<br/>GitHub-Issue, GitLab-Issue] -->|Polling| B[TicketSource]
    B --> C[TicketQueue<br/>Dedup + Claim]
    C --> D[WorkspaceManager<br/>git worktree]
    D --> E[AgentBackend<br/>claude / codex]
    E --> F[GitOps<br/>commit + push]
    F --> G[ResultReporter<br/>PR/MR + Kommentar]

    Wofür ist das?¶

    Beispiel 1 — Fresh-Pipeline: Du legst ein GitHub-Issue an mit:

    „Erzeuge eine HELLO.md mit Inhalt 'Hallo aus Agentry' und committe sie."

    — versiehst es mit dem Label agent-task, und 2 Minuten später hast du einen Pull Request, der genau das tut.

    Beispiel 2 — Revise-Pipeline: Reviewer hinterlässt am vom Agent erstellten PR Kommentare („Bitte zusätzlich Edge-Case X testen"), setzt Label agent-revise — und der Agent iteriert auf demselben Branch weiter, bis der Reviewer zufrieden ist.

    Status¶

    In Produkt-Entwicklung. Sub-Nummerierung pro Phase startet bei .1; die ursprüngliche chronologische Phase-Liste mit Datum + Begründung steht in CLAUDE.md.

    Phase 1 — Härtung ✅¶

    Multi-Repo / Account-Scope, Konfigurations-Validierung beim Start, strukturierte Fehler mit Pipeline-Phasen, Timeout pro Agent-Run, Crash-Recovery für hängende Tickets. Feature-Seiten: Multi-Repo · Konfig-Validierung · Fehler-Handling · Timeout · Crash-Recovery.

    Phase 2 — Beobachtbarkeit & Sicherheit ✅¶

    • 2.1 Log-Persistenz — rotierender File-Sink, Level + Pfad konfigurierbar, parallel zu stdout.
    • 2.2 Health-/Status-Endpoint — swift-nio-Server mit /healthz//readyz//status.
    • 2.3 Metriken — /metrics im Prometheus- Text-Format, Counter und Gauges.
    • 2.4 Sandbox-Plugin-Architektur:
      • 2.4a SandboxStrategy-Protocol + SandboxRouter mit Label-Override / Rules / Default, Capability-Discovery beim Start.
      • 2.4b LinuxBwrapStrategy — bwrap mit System-RO-Binds, tmpfs für /tmp/$HOME, PID-/UTS-/IPC-Namespaces.
      • 2.4c MacOSSandboxStrategy — sandbox-exec mit eingebettetem .sb-Profil (deny default für Writes, Allowlist für Workspace).
    • 2.5 Token-Handling — 3-Quellen- Hierarchie (AGENTRY_GITHUB_TOKEN-Env / 0600-Datei / gh auth token-Fallback), Weitergabe an Subprozesse via GH_TOKEN.

    Phase 3 — Skalierung ✅¶

    • 3.1 Codex-Backend — @openai/codex- CLI als zweites AgentBackend neben Claude Code, gemeinsamer AgentPromptBuilder.
    • 3.2 Parallele Worker — Producer/Consumer mit AsyncStream<Ticket>, maxConcurrency konfigurierbar, atomarer TicketQueue.claim() gegen Doppel-Trigger.
    • 3.3 Webhooks — POST /webhook/github (HMAC-SHA256) und POST /webhook/gitlab (Plain-Token + UUID-Replay- Schutz), parallel zum Polling über gemeinsamen TicketIntake.
    • 3.4 PR-Review-Loop — agent-revise- Label auf PR/MR triggert inkrementellen Lauf auf demselben Head-Branch, beliebig viele Iterationen.
    • 3.5 GitLab-Source — Single-Project, Multi-Project, Group-Scope (inkl. Subgruppen), MR-Revise-Loop, Crash-Recovery via API, GitLab-Webhooks mit Plain-Token-Verify.
    • 3.6 Pro-Ticket-Routing — agent:backend:<id> und agent:model:<wert> mit agentBackends/agentModels-Allowlists; ohne Allowlist Routing aus (Default-Verhalten unverändert).

    Phase 4 — Distribution ✅¶

    • 4.1 Service-Modus-Templates — packaging/launchd/ (macOS-User-Agent) und packaging/systemd/ (User- oder System-Service) mit Auto-Restart und Logging-Integration.
    • 4.2 Packaging — Multi-Stage-Dockerfile, Homebrew-Formula-Template, Release-Workflow für macOS-arm64 + Linux-x86_64-Binaries bei v*-Tags, Docker-Build-Smoke-Test.
    • 4.3 CLI-Subcommands — agentry init, config validate/show, status, logs, webhook install/list/delete, labels install/delete, version, help neben daemon (Default, backwards-kompatibel).
    • 4.4 Auto-Setup — agentry webhook install und agentry labels install legen Hooks bzw. Status-/Trigger-/Routing- Labels via gh api/glab api an, idempotent, Watch-aware (Single-/Multi-Repo, GitLab Group-Hook). Siehe Webhooks und CLI.
    • 4.5 Linux-CI — .github/workflows/ci.yml baut und testet bei jedem Push/PR auf macOS-14 und ubuntu-22.04 (swift:6.3-jammy-Container) parallel.
    • 4.6 Metriken-Erweiterung + HEAD-Support — Histogram agentry_agent_run_duration_seconds, Per-Backend-Counter agentry_tickets_*_by_backend_total, HEAD-Method auf allen Health-/Metrics-Endpoints. Siehe Metriken.
    • 4.7 Keychain / libsecret / Rotation — macOS-Keychain (Security.framework) und Linux-libsecret (secret-tool lookup) als zusätzliche Token-Quellen, Config.tokenSource ("env"/"keychain"/"libsecret"/"file"/"cli") zur Source- Erzwingung, TokenRotator mit SIGHUP-Listener für Live-Rotation. Siehe Token-Handling.

    Wichtige Vokabeln¶

    Begriff Bedeutung
    Ticket Plattform-neutrales Domänen-Modell für eine Aufgabe. Aus GitHub-Issues oder GitLab-Issues geparsed; künftig auch Jira/ServiceNow.
    TicketTrigger .fresh (Issue → PR) vs .revise(head, base) (PR-Iteration). Vom Source-Layer gesetzt, vom Daemon ausgewertet.
    TicketSource Quelle für Tickets — Protocol mit konkreten Implementierungen pro Quellsystem.
    AgentBackend Konkrete AI-Agent-Implementierung — heute claude-code und codex, weitere via Protocol erweiterbar.
    ResultReporter Schreibt zurück ans Quellsystem (Labels, Kommentare, PR/MR-Create) — Protocol mit GitHub- und GitLab-Implementierungen.
    agent-task Trigger-Label für Issues; ohne dieses Label tut Agentry für die Fresh-Pipeline nichts.
    agent-revise Trigger-Label für PRs/MRs; löst die Revise-Pipeline aus.
