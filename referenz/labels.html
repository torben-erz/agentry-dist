    Label-Referenz¶

    Agentry kommuniziert Status über GitHub-Labels. Diese Seite ist die Wahrheit über die aktuelle Label-Konvention.

    Trigger-Labels¶

    Label Farbe Auf Bedeutung
    agent-task #1d76db (blau) Issue „Bitte bearbeiten." Der Daemon nimmt das Ticket auf, sobald er es sieht.
    agent-revise #5319e7 (lila) PR „Bitte überarbeiten." Reviewer setzt es nach einem Review; der Daemon iteriert auf demselben Branch.

    Konfigurierbar via triggerLabel und reviseLabel. Die Status-Labels unten sind aktuell nicht umbenennbar.

    Status-Labels¶

    stateDiagram-v2
    state "Fresh" as fresh {
        [*] --> agent_task: User setzt
        agent_task --> agent_in_progress: Daemon nimmt auf
        agent_in_progress --> agent_done: Erfolgreich
        agent_in_progress --> agent_failed: Fehler
        agent_failed --> agent_task: User triggert neu
        agent_done --> [*]
    }
    state "Revise (auf PR)" as revise {
        [*] --> agent_revise: Reviewer setzt
        agent_revise --> agent_revising: Daemon nimmt auf
        agent_revising --> agent_revised: Erfolgreich gepusht
        agent_revising --> agent_revise_failed: Fehler
        agent_revised --> agent_revise: Reviewer triggert neu
        agent_revise_failed --> agent_revise: Reviewer triggert neu
    }
    Label Farbe Bedeutung Wird gesetzt von
    agent:in-progress #fbca04 (gelb) Daemon arbeitet gerade an einem Fresh-Issue Daemon.processFresh
    agent:done #0e8a16 (grün) Fresh-Pipeline erfolgreich abgeschlossen, ggf. mit PR Daemon.finalizeFresh
    agent:failed #d93f0b (rot) Fresh-Pipeline-Fehler in einer Phase Daemon.reportFreshFailure
    agent:revising #fbca04 (gelb) Daemon arbeitet gerade an einer PR-Revision Daemon.processRevise
    agent:revised #0e8a16 (grün) Letzte PR-Revision erfolgreich abgeschlossen Daemon.finalizeRevise
    agent:revise-failed #d93f0b (rot) Letzte PR-Revision in einer Phase fehlgeschlagen Daemon.reportReviseFailure

    Routing-Labels (Pro-Ticket)¶

    Pro Ticket lässt sich das Backend bzw. das Modell per Label überschreiben, sofern der Operator das in der Config zugelassen hat. Sicherheitsmodell: explizite Allowlist in Config.agentBackends / Config.agentModels. Ohne Allowlist sind die Routing-Labels stumm — der Daemon nutzt agentBackend und agentModel.

    Label-Präfix Bedeutung Allowlist
    agent:backend:<id> Wähle für dieses Ticket ein anderes Agent-Backend (z. B. agent:backend:codex). Config.agentBackends
    agent:model:<wert> Wähle für dieses Ticket ein anderes Modell (z. B. agent:model:claude-opus-4-7). Config.agentModels
    agent:sandbox:<id> Wähle eine andere Sandbox-Strategie (z. B. agent:sandbox:macos-sandbox). Config.sandbox.rules/default

    Verhalten bei Verstoß: Wenn ein Label auf ein Backend/Modell zeigt, das nicht in der Allowlist ist, wird das Label ignoriert + geloggt (AgentRouter fällt auf den Default zurück). Damit failt ein Ticket nicht plötzlich, nur weil der Operator die Allowlist gekürzt hat. Details siehe Pro-Ticket-Routing.

    Filter-Verhalten¶

    TicketFilter.ready(_:kind:) filtert vor der Verarbeitung — je nach Polling-Modus mit anderen Regeln:

    Fresh-Modus (PollKind.freshIssue):

    • ✅ Label agent-task (oder das konfigurierte triggerLabel) trägt
    • ❌ kein agent:done, agent:failed, agent:in-progress trägt
    • ❌ kein Pull Request ist (GitHub mischt Issues und PRs im Endpoint)

    Revise-Modus (PollKind.revisePR):

    • ✅ Label agent-revise (oder das konfigurierte reviseLabel) trägt
    • ✅ ist ein Pull Request
    • ❌ kein agent:revising trägt (sonst läuft schon eine Revision)
    • agent:revised und agent:revise-failed blocken nicht — sie zeigen nur den Status der vorigen Iteration. Setzt der Reviewer agent-revise erneut, beginnt eine neue Iteration.

    Ein gescheitertes Ticket erneut triggern¶

    Standardweg:

    gh issue edit <n> -R <repo> --remove-label "agent:failed"

    agent-task bleibt bei Fehlschlag bewusst auf dem Issue — entfernen von agent:failed reicht für den Re-Trigger. Beim nächsten Polling läuft die Pipeline erneut. Beachte: Der Branch agent/ticket-<n> existiert eventuell schon im Repo — der WorkspaceManager löscht ihn dann und legt ihn neu an.

    Verhalten nach erfolgreicher Bearbeitung¶

    Bei erfolgreichem Abschluss entfernt der Daemon sowohl agent:in-progress als auch agent-task (das konfigurierte triggerLabel) und setzt agent:done. Effekt: das Issue verschwindet sofort aus dem ?labels=agent-task-Polling-Filter — kein 1–3-Minuten-„noch sichtbar"-Lag, bis GitHubs Issues-Index das agent:done mitbekommt. Bei Fehlschlag bleibt agent-task dagegen drauf (siehe oben — der Re-Trigger über agent:failed ohne Label-Neusetzen ist gewollt).

    Alternative: Das Ticket schließen und ein neues anlegen (sauberer Ticket-Lebenszyklus, neue Nummer, neuer Branch).

    Labels initial anlegen¶

    Einmaliges Setup für jedes Ziel-Repo:

    REPO=<owner>/<repo>
gh label create "agent-task"         --color "1d76db" -R "$REPO" \
    --description "Trigger: dieses Issue soll von einem Agent bearbeitet werden"
gh label create "agent-revise"       --color "5319e7" -R "$REPO" \
    --description "Trigger: dieser PR soll vom Agent überarbeitet werden"
gh label create "agent:in-progress"  --color "fbca04" -R "$REPO" \
    --description "Fresh-Pipeline: wird gerade bearbeitet"
gh label create "agent:done"         --color "0e8a16" -R "$REPO" \
    --description "Fresh-Pipeline: erfolgreich abgeschlossen"
gh label create "agent:failed"       --color "d93f0b" -R "$REPO" \
    --description "Fresh-Pipeline: fehlgeschlagen"
gh label create "agent:revising"     --color "fbca04" -R "$REPO" \
    --description "Revise-Pipeline: wird gerade überarbeitet"
gh label create "agent:revised"      --color "0e8a16" -R "$REPO" \
    --description "Revise-Pipeline: erfolgreich überarbeitet"
gh label create "agent:revise-failed" --color "d93f0b" -R "$REPO" \
    --description "Revise-Pipeline: fehlgeschlagen"

    Routing-Labels werden nur bei Bedarf angelegt — und nur jene, die der Operator via Allowlist freigeschaltet hat. Beispiel:

    # Backend-Routing aktivieren (bei agentBackends: ["claude-code", "codex"])
gh label create "agent:backend:claude-code" --color "5319e7" -R "$REPO" \
    --description "Routing: dieses Ticket mit Claude Code bearbeiten"
gh label create "agent:backend:codex"       --color "5319e7" -R "$REPO" \
    --description "Routing: dieses Ticket mit Codex bearbeiten"

# Modell-Routing aktivieren (bei agentModels: [...])
gh label create "agent:model:claude-opus-4-7"   --color "ededed" -R "$REPO"
gh label create "agent:model:claude-sonnet-4-6" --color "ededed" -R "$REPO"

    Label-Setup automatisieren¶

    Statt der manuellen gh label create-Befehle oben legt agentry labels install alle Status-, Trigger- und (wenn Allowlist aktiv) Routing-Labels pro Watch-Ziel an — idempotent, GitHub und GitLab. Details siehe CLI: agentry labels install.

    agentry labels install

    Labels wieder entfernen¶

    agentry labels delete ist das Gegenstück und entfernt die vom Daemon erwarteten Labels aus jedem Watch-Ziel — idempotent (notFound ist kein Fehler). Sinnvoll, wenn ein Repo nicht mehr vom Daemon bedient wird oder die Routing-Allowlist gekürzt wurde und Routing-Labels in der UI tot herumliegen.

    agentry labels delete                                # alle Daemon-Labels aus allen Watch-Zielen
agentry labels delete --dry-run                      # Plan-Vorschau ohne API-Aufruf
agentry labels delete --name agent:done              # nur ein einzelnes Label
agentry labels delete --target github-repo:foo/bar   # auf ein Watch-Ziel einschränken

    Destruktiv

    gh label delete / glab label delete entfernen das Label gleichzeitig von allen Issues/PRs, die es tragen — Status-Tracking ist danach weg. Vor dem Aufruf bewusst entscheiden, ob die Watch-Ziele nicht mehr vom Daemon bedient werden.

    --name ist auf die in dieser Referenz aufgelisteten Labels beschränkt; freie Namen werden mit Liste der gültigen Werte abgelehnt. Details siehe CLI: agentry labels delete.
