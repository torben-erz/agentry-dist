    Konfigurations-Referenz¶

    Vollständige Liste aller ~/.agentry/config.json-Schlüssel.

    Komplettes Beispiel¶

    {
  "provider": "github",
  "host": null,
  "watch": { "type": "repo", "value": "torben-erz/Agentry" },
  "baseBranch": null,
  "pollInterval": 5,
  "agentTimeoutSeconds": 1800,
  "maxConcurrency": 1,
  "agentBackend": "claude",
  "agentModel": null,
  "reposCacheDir": "~/.agentry/repos",
  "workspaceRoot": "~/.agentry/workspaces",
  "stateFile": "~/.agentry/state.json",
  "etagDir": "~/.agentry/etags",
  "triggerLabel": "agent-task",
  "reviseLabel": "agent-revise",
  "reviseEnabled": true,
  "agentBanner": true,
  "logLevel": "info",
  "logFile": "~/.agentry/agentry.log",
  "logMaxBytes": 10485760,
  "logMaxFiles": 5,
  "healthEnabled": true,
  "healthHost": "127.0.0.1",
  "healthPort": 8765,
  "webhookEnabled": false,
  "webhookHost": "127.0.0.1",
  "webhookPort": 8766,
  "webhookSecretFile": null
}

    Schlüssel im Detail¶

    provider (string, default "github")¶

    Quellsystem-Provider. Aktuell: "github" oder "gitlab". Bestimmt:

    • welche TicketSource und welcher ResultReporter aktiv sind
    • welche CLI als Vendor-Werkzeug erwartet wird (gh vs glab)
    • welche Token-Env-Variable (AGENTRY_GITHUB_TOKEN vs AGENTRY_GITLAB_TOKEN)
    • welche Watch-Pfad-Form akzeptiert wird (Mehrstufigkeit nur bei GitLab)

    Validator weist beim Start ab, wenn provider unbekannt ist.

    Details: GitLab als zweite Quelle.

    host (string?, default null)¶

    Hostname der Provider-Instanz. null → Provider-Default (github.com bzw. gitlab.com). Für selbst-gehostete Instanzen den eigenen Hostnamen ohne api.-Präfix setzen:

    Provider host API-URL, die Agentry verwendet
    GitHub.com null (oder weglassen) https://api.github.com
    GitHub Enterprise Server "github.example.com" https://github.example.com/api/v3
    GitLab.com null (oder weglassen) https://gitlab.com/api/v4
    Self-hosted GitLab "gitlab.example.com" https://gitlab.example.com/api/v4

    Der gleiche Host wird auch als HTTPS-Clone-URL-Host verwendet (https://<host>/<owner>/<repo>.git). Voraussetzung für GHES: gh auth login --hostname <host> (siehe Erste Schritte).

    watch (erforderlich, eine der drei Formen)¶

    Form JSON Beschreibung
    Single-Repo {"type": "repo", "value": "owner/name"} Pollt ein Repo
    Multi-Repo {"type": "repos", "value": ["a/b", "c/d"]} Liste konkreter Repos
    OwnerScope {"type": "ownerScope", "value": "owner"} Alle Repos eines Accounts/Org via Search-API

    Backwards-Compat / Shortcuts: Top-Level-"repo": "owner/name" wird zu {"type": "repo", "value": "owner/name"} interpretiert. Zusätzlich akzeptiert der Decoder "watch": "owner/name" als String-Shortcut für Single-Repo (gleiche Bedeutung wie die Object-Form). Multi-Repo und OwnerScope brauchen die ausführliche Object-Form.

    baseBranch (optional)¶

    Wert Verhalten
    null (Default) Pro Repo automatisch via gh api repos/<repo> --jq .default_branch ermittelt, gecacht in der WorkspaceManager-Instanz
    "main" Erzwingt diesen Branch global für alle überwachten Repos

    Setze, wenn du explizit von einem anderen Branch abzweigen willst (z. B. develop als Integrationszweig).

    pollInterval (Sekunden, default 5)¶

    Validierung: > 0. Warnung bei < 2 (Rate-Limit-Risiko bei vielen Repos).

    Wert Wann
    5 (Default) Single-Repo, normale Reaktionszeit
    2-3 Schnellere Reaktion, höheres API-Volumen
    30+ Schonend, sichtbarer Lag

    agentTimeoutSeconds (Sekunden, default 1800)¶

    Maximale Laufzeit pro Agent-Lauf. Bei Überschreitung: SIGTERM an den Subprozess, Ticket bekommt agent:failed. Validierung: > 0. Warnung bei < 60.

    maxConcurrency (int, default 1)¶

    Anzahl paralleler Worker. 1 ist die historische, serielle Pipeline. Bei > 1 werden mehrere Tickets gleichzeitig verarbeitet — jeder Worker bekommt einen eigenen Worktree. Validator: > 0; Warnung bei > 8 (typisch saturieren 4–8 Worker bereits CPU/IO und API-Quota).

    Details: Parallele Worker.

    agentBackend (string, default "claude")¶

    Aktuell unterstützt: claude (Default) und codex. Bei unbekanntem Wert lehnt der Validator beim Start ab.

    Details: - claude — Anthropic Claude Code CLI - codex — OpenAI Codex CLI

    agentModel (string?, default null)¶

    Optional. Wenn gesetzt, wird der Wert als --model <wert> an die Vendor-CLI weitergereicht. Beispielwerte:

    Backend Mögliche Werte (Auswahl, Stand 2026)
    claude claude-opus-4-7, claude-sonnet-4-6, claude-haiku-4-5-20251001
    codex gpt-5-codex

    Validator prüft nur, dass der Wert nicht leer ist und keine Whitespace-Reste am Rand hat — keine Allowlist, weil sich Modell-Namen schnell ändern. Was die CLI mit unbekannten Modellen anstellt (akzeptieren, anderen Namen verlangen, Fehler), ist Sache der CLI.

    null (Default) → CLI nutzt ihren eingebauten Default.

    Details siehe Backend-Doku (Codex, Claude ist in AgentBackend erklärt).

    agentBackends (string[]?, default null)¶

    Allowlist für Pro-Ticket-Backend-Routing via agent:backend:<id>-Label.

    • null (Default) → Routing aus, nur agentBackend läuft.
    • Nicht-leere Liste → nur die genannten Backends dürfen via Label aktiviert werden. agentBackend muss in der Liste enthalten sein; sonst lehnt der Validator ab.

    Beispiel:

    {
  "agentBackend": "claude",
  "agentBackends": ["claude", "codex"]
}

    Damit ist agent:backend:codex auf einem Ticket wirksam; alles andere fällt auf claude zurück. Siehe Pro-Ticket-Routing.

    agentModels (string[]?, default null)¶

    Allowlist für Pro-Ticket-Modell-Routing via agent:model:<wert>-Label.

    • null (Default) → Modell-Routing aus, nur agentModel läuft.
    • Nicht-leere Liste → nur die genannten Modell-Werte dürfen via Label aktiviert werden. Werte werden in Form geprüft (nicht leer, kein Whitespace) — keine Vendor-Allowlist.

    Beispiel:

    {
  "agentModel": "claude-sonnet-4-6",
  "agentModels": ["claude-sonnet-4-6", "claude-opus-4-7", "gpt-5-codex"]
}

    reposCacheDir (Pfad, default ~/.agentry/repos)¶

    Wohin Bare-Caches geclont werden. Pro Repo entsteht ein <owner>-<repo>.git-Verzeichnis darin.

    workspaceRoot (Pfad, default ~/.agentry/workspaces)¶

    Wohin temporäre Worktrees angelegt werden. Pro Ticket entsteht <owner>-<repo>-ticket-<n>/. Wird nach Abschluss aufgeräumt.

    stateFile (Pfad, default ~/.agentry/state.json)¶

    Persistente Liste verarbeiteter Tickets. Format:

    { "processed": ["owner/name#1", "owner/name#2", "other/repo#1"] }

    etagDir (Pfad, default ~/.agentry/etags)¶

    Pro Watch-Endpoint eine ETag-Datei:

    Source-Typ ETag-Datei
    Single-Repo / Multi-Repo <owner>-<repo>.etag
    OwnerScope owner-<owner>.etag

    triggerLabel (string, default "agent-task")¶

    Welches Label ein Ticket tragen muss, damit der Daemon es bearbeitet. Status-Labels (agent:in-progress, agent:done, agent:failed) sind fest und nutzen ihre Standardnamen unabhängig von dieser Einstellung.

    reviseLabel (string, default "agent-revise")¶

    Label, mit dem ein Reviewer einen bestehenden PR in den Revise-Loop schickt. Muss sich von triggerLabel unterscheiden — Validator weist Kollisionen ab. Status-Labels für Revise sind agent:revising, agent:revised, agent:revise-failed.

    reviseEnabled (bool, default true)¶

    PR-Review-Loop aktiv? Wenn false, wird das agent-revise-Polling komplett abgeschaltet — der Daemon ignoriert das Label vollständig.

    Details: PR-Review-Loop.

    agentBanner (bool, default true)¶

    Steuert die Banner-Zeile als Prefix in PR-Body, Issue-/PR-Kommentaren und Commit-Message-Bodies plus den Co-Authored-By:-Trailer im Commit.

    Wert Verhalten
    true (Default) Jeder Kommentar/PR/Commit bekommt eine erste Zeile à la 🟧 **Claude Code** · backtick-claude-opus-4-7-backtick. Commits haben zusätzlich einen Co-Authored-By:-Trailer (Claude Code via Agentry (modell) <noreply@anthropic.com> bzw. Codex via Agentry (modell) <noreply@openai.com>) — GitHub/GitLab zeigt damit einen Sekundär-Avatar im Commit-View.
    false Nackte Kommentare und Commits ohne Banner und ohne Co-Author-Trailer — Verhalten wie vor Beta-13.

    Sinnvoll auf false, wenn:

    • du den Sekundär-Avatar im Commit-View nicht haben möchtest,
    • du eigene Bot-Accounts pro Backend einsetzt (Token-Pfad), deren Identität sich ohnehin am Author-Slot des Kommentars zeigt — der Banner wäre dann redundant,
    • du Kommentare „nackt" für Compliance-/Review-Tooling brauchst.

    Plattform-agnostisch — wirkt bei GitHub, GitLab und kommenden Providern gleichermaßen (Banner ist plain Markdown, Co-Authored-By: ist Git-Convention).

    Logging-Felder¶

    Schlüssel Default Bedeutung
    logLevel "info" debug/info/warn/error (case-insensitive) — Schwelle für stdout und File.
    logFile ~/.agentry/agentry.log Pfad. null deaktiviert File-Logging.
    logMaxBytes 10485760 (10 MB) Größe pro Datei vor Rotation.
    logMaxFiles 5 Anzahl Backup-Dateien. 0 = keine Backups.

    Details: Logging.

    Health-/Status-Endpoint¶

    Schlüssel Default Bedeutung
    healthEnabled true HTTP-Server für /healthz//readyz//status starten?
    healthHost "127.0.0.1" Bind-Adresse — Default nur lokal aus Sicherheitsgründen.
    healthPort 8765 TCP-Port (1–65535).

    Details: Health-Endpoint.

    Webhook-Endpoint¶

    Schlüssel Default Bedeutung
    webhookEnabled false Wenn true, startet zusätzlich zum Polling ein HTTP-Server für GitHub-Webhooks.
    webhookHost "127.0.0.1" Bind-Adresse. Für realen Webhook-Empfang 0.0.0.0 mit Reverse-Proxy davor.
    webhookPort 8766 TCP-Port. Muss sich von healthPort unterscheiden.
    webhookSecretFile null Optional, Pfad zu 0600-Datei mit dem HMAC-Secret. Wenn null UND AGENTRY_WEBHOOK_SECRET nicht gesetzt: WebhookServer startet nicht.

    Details: Webhooks.

    Token-Handling¶

    Schlüssel Default Bedeutung
    tokenFile null Pfad zu einer 0600-Datei mit dem GitHub-PAT. null → Fallback auf Env-Variable AGENTRY_GITHUB_TOKEN oder gh auth token.

    Details: Token-Handling.

    Update-Notifier¶

    Schlüssel Default Bedeutung
    updateCheckEnabled true An/aus-Schalter für den Update-Notifier. Bei true initialer Check beim Daemon-Start + periodischer Re-Check im konfigurierten Intervall. Loggt WARN bei verfügbarem Update; Fehler werden silent als Debug geloggt. Kein Auto-Update. Bei false: kein Netzwerk-Call.
    updateCheckIntervalSeconds 86400 (24 h) Abstand zwischen periodischen Re-Checks. Mindestens 60 s (wird intern geklemmt). Erster Check erfolgt sofort beim Daemon-Start, unabhängig vom Intervall.
    updateCheckRepo "torben-erz/agentry-dist" GitHub-Repo (owner/name), gegen den der Notifier prüft. Default zeigt auf das öffentliche Distribution-Repo. Operator kann das auf Fork, On-Prem-Mirror oder separate Schiene umstellen.

    Details: Update-Notifier.

    Auth-Watchdog¶

    Periodischer Health-Check der Vendor-CLI-Auth (claude, codex), um OAuth-Token-Ablauf vor dem nächsten Ticket sichtbar zu machen.

    Schlüssel Default Bedeutung
    authWatchdogEnabled false An/aus-Schalter. Bei true startet eine Detached-Task parallel zum Polling: Initial-Check sofort + periodischer Re-Check im konfigurierten Intervall. Bei false: kein Check, keine agentry_auth_*-Metriken im /metrics-Output.
    authWatchdogIntervalSeconds 3600 (1 h) Abstand zwischen Checks. Mindestens 60 s (wird intern geklemmt — kürzere Intervalle erzeugen unnötig Rate-Limit-Druck ohne praktischen Nutzen).

    Auto-Detect der Check-Strategie pro Backend:

    • ANTHROPIC_API_KEY im Env → HTTP GET auf api.anthropic.com/v1/models (gratis, keine Token-Kosten).
    • OPENAI_API_KEY im Env → HTTP GET auf api.openai.com/v1/models (gratis).
    • Sonst → CLI-Smoke-Test (claude -p "OK" bzw. codex exec ... "OK" mit 30 s Timeout). Verbraucht ein paar Subscription-Tokens, kostet aber bei OAuth-Subscriptions kein Geld.

    Single-Shot via agentry auth check (kein Daemon nötig). Details: Auth-Watchdog.

    Sandbox¶

    Schlüssel Default Bedeutung
    sandbox.default Plattform-abhängig: "macos-sandbox" (macOS) / "linux-bwrap" (Linux) / "none" (sonst) Sandbox-Strategie, die greift wenn weder Label-Override noch Rule matched. Out-of-the-box läuft der Daemon gesandboxed; auf Linux ist bwrap Voraussetzung (apt install bubblewrap). Fehlt sie, startet der Daemon mit SandboxError.defaultUnavailable statt still ungeschützt zu laufen.
    sandbox.strategies {} Pro Strategie ein Options-Bag (z. B. profile-Pfad für macos-sandbox, engine+image für linux-container).
    sandbox.rules [] Routing-Regeln {ifLabel, use}. Erste matchende gewinnt.

    Details: Sandbox.

    Pfad-Expansion¶

    Alle Pfad-Schlüssel unterstützen ~/ als Home-Verzeichnis-Expansion. Andere Tilde-Patterns (~user/) werden nicht unterstützt.

    Validierung¶

    Alle Schlüssel werden beim Daemon-Start strukturell geprüft:

    • Repo-Identifier: genau ein Slash, beide Teile nicht leer, kein Whitespace
    • Owner: kein Slash, kein Whitespace, nicht leer
    • Pfade: Eltern-Verzeichnis muss existieren oder anlegbar sein, Schreibtest
    • Backend: muss in ConfigValidator.supportedBackends stehen
    • Numerische Werte: > 0

    Beim ersten ungültigen Wert → Abbruch mit Fehlermeldung. Mehr: Konfig-Validierung.
