    Eine neue TicketSource hinzufügen¶

    Diese Anleitung beschreibt, wie eine neue Quellsystem-Anbindung (z. B. GitLab oder Jira) hinzugefügt wird. Die heutige GitHub-Anbindung dient als Vorlage.

    Schritt-Übersicht¶

    flowchart TB
    A[1. Domain-Mapping<br/>Quelle → Ticket] --> B[2. WatchTarget-Variante]
    B --> C[3. Source-Implementierung<br/>im neuen Sub-Ordner]
    C --> D[4. Factory-Switch]
    D --> E[5. ResultReporter-Anpassung<br/>oder neuer Reporter]
    E --> F[6. CrashRecovery-Erweiterung]
    F --> G[7. ConfigValidator]
    G --> H[8. Tests]
    H --> I[9. Doku]

    1. Domain-Mapping¶

    Schau zuerst auf das Quellsystem-Format und mappe es auf Ticket:

    Ticket-Feld GitLab Jira
    number iid (Int) key (String! → ggf. eigenes Feld nötig)
    title title summary
    body description description (ADF/Plain)
    labels labels labels
    htmlURL web_url self-URL
    repository <group>/<project> Project-Key
    pullRequest n/a (Merge Requests sind eigene API) n/a

    ID-Typ

    Falls die Quelle keine numerische ID hat (Jira: PROJ-123), brauchen wir entweder einen Sum-Type oder ein zweites Feld Ticket.id: String. Heutiges number: Int funktioniert nur für GitHub/GitLab.

    2. WatchTarget-Variante¶

    Neuer Case in WatchTarget:

    enum WatchTarget {
    case repo(String)
    case repos([String])
    case ownerScope(String)
    case gitlabProject(String)        // ← neu
}

    Codable + description ergänzen.

    3. Source-Implementierung¶

    Neuer Sub-Ordner Sources/agentry/GitLab/:

    Sources/agentry/GitLab/
├── GitLabClient.swift
└── GitLabProjectSource.swift

    GitLabClient analog zu GitHubClient — URLSession-Wrapper, ETag-Support, Token-Auflösung (glab auth status oder PAT aus Config).

    GitLabProjectSource: TicketSource:

    final class GitLabProjectSource: TicketSource, Sendable {
    let client: GitLabClient
    let project: String
    let label: String
    let etagFile: URL

    func pollOnce() async throws -> [Ticket] {
        // GET /projects/<urlencoded>/issues?labels=<label>&state=opened
        // ETag prüfen, JSON dekodieren, in Ticket mappen, IssueFilter.ready
    }
}

    4. Factory-Switch¶

    TicketSourceFactory.make ergänzen:

    case .gitlabProject(let project):
    let client = try await GitLabClient.resolve(/* … */)
    return GitLabProjectSource(client: client, project: project, config: config)

    Falls die Initialisierung async/throws ist, wird die Factory-Signatur async/throws — Daemon-Init muss das spiegeln.

    5. ResultReporter¶

    Heute ist ResultReporter GitHub-spezifisch (nutzt gh-CLI). Optionen:

    Option Beschreibung
    Refactor zu Protocol protocol ResultReporter, GitHub und GitLab als Implementierungen. Sauber.
    Erweiterung ResultReporter bekommt eine Backend-Property und delegiert intern. Pragmatisch.
    Pro Source eigener Reporter Daemon bekommt einen Reporter, der zur Source passt — wird beim Init zusammen ausgewählt.

    Empfehlung: Protocol-Refactor sobald die zweite Source kommt — ist klein und macht weitere Erweiterungen sauber.

    6. CrashRecovery¶

    CrashRecovery.fetchHangingTickets und markAsFailed müssen die neue Quelle bedienen. Pro WatchTarget-Variante einen Fall im switch.

    7. ConfigValidator¶

    validateWatch ergänzen für die neue Variante. Format-Prüfung, Whitespace, Slashes — was auch immer das Quellsystem verlangt.

    EnvironmentCheck.run anpassen, falls neue Tools nötig sind (glab für GitLab CLI, etc.) — und das CLI als Voraussetzung in der Installations-Doku nachtragen.

    8. Tests¶

    Pro neue Quelle mindestens:

    • JSON-Parsing-Test (Mock-Response → Ticket)
    • WatchTarget-Codable-Test für die neue Variante
    • ConfigValidator-Test für Format-Edge-Cases

    9. Doku¶

    • Neue Seite unter docs/architektur/ oder docs/features/ (z. B. gitlab-source.md)
    • Erwähnen in Architektur-Übersicht und TicketSource
    • Konfiguration: neue watch-Variante dokumentieren
    • Installation: zusätzliches CLI ergänzen, falls nötig

    Sanity-Check¶

    • swift build clean
    • swift test grün, neue Tests sind dabei
    • Manueller E2E-Test gegen ein echtes Test-Ticket im Quellsystem
    • CLAUDE.md updated mit dem neuen Source-Ordner
