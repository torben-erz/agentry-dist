    Umbenennung & Owner-Wechsel — Playbook¶

    Diese Seite ist ein Wartungs-Playbook für zwei hypothetische, aber realistische Szenarien:

    1. Owner-Wechsel — die drei Agentry-Repos (Agentry, agentry-dist, homebrew-agentry) wandern von torben-erz zu einem anderen GitHub-Owner (Org, Firmen-Account, neuer Personal-Account).
    2. Produktname-Wechsel — der Name Agentry / agentry muss aus rechtlichen, strategischen oder Markenrecherche-Gründen ersetzt werden.

    Beide Schritte sind heute nicht geplant. Die Seite existiert, damit ein zukünftiger Maintainer (oder zukünftiges Ich) den Umfang in unter einer Stunde überblicken kann.

    Trigger-Anlässe¶

    Szenario Auslöser
    Owner-Wechsel Übergabe an eine Firmen-Org, Co-Founder-Konstellation, dedizierte Agentry-Org, Bus-Faktor-Risiko
    Namens-Wechsel Markenrecherche-Treffer (DPMA/EUIPO), juristische Abmahnung, strategischer Rebrand vor Stufe 1

    Timing-Faustregel: Beide Schritte sind vor Stufe 1 (Source-Repo öffentlich, siehe Vertriebsmodelle) billig. Nach Stufe 1 wachsen die externen Referenzen (Blogposts, Foren, Kundendoku) und der Aufwand steigt nichtlinear. Im Zweifel: jetzt machen.

    Teil A — Owner-Wechsel (torben-erz → <NEW_OWNER>)¶

    Owner-Wechsel ist der deutlich harmlosere der beiden Schritte, weil GitHub für umbenannte oder transferierte Repos automatische 301-Redirects liefert. Bestehende git remote-URLs, brew tap-Befehle, gh api-Aufrufe und Web-Bookmarks der Tester funktionieren weiter.

    A.1 Was automatisch redirected (kein Bruch)¶

    • brew tap torben-erz/agentry und alte Formula-Download-URLs
    • git clone / git pull mit alten Remotes
    • Web-Links in alter Doku, Blogposts, Beta-Einladungen
    • gh api /repos/torben-erz/... (folgt dem Redirect)

    A.2 Was aktiv angefasst werden muss¶

    Hardcodierte Defaults im Code (grep -rn "torben-erz" Sources/):

    • Sources/agentry/Config.swift — Default-watch und updateCheckRepo (in Config.default und Decoder-Default)
    • Sources/agentry/UpdateNotifier.swift — defaultRepoSlug
    • Sources/agentry/CLI.swift — Help-Text mit Doku-URL + Template-String in init-Subcommand (schreibt den Slug in die generierte config.json)
    • Sources/agentry/ConfigValidator.swift — nur Beispiel in einer Error-Message, kosmetisch

    CI / Release-Workflow (.github/workflows/release.yml):

    • GH_REPO-Env (Tarball-Upload-Ziel, zweimal)
    • repository:-Feld im Tap-Push-Step (Formula-Update-Ziel)
    • Cross-Repo-PAT (GH_PAT_DIST, GH_PAT_TAP o. ä.) muss unter <NEW_OWNER> neu ausgestellt sein oder die Org-Mitgliedschaft beide Repos abdecken
    • git config user.email "noreply@nanoapes.com" ist entkoppelt vom Owner — nur ändern, wenn auch die Firma wechselt

    Packaging:

    • packaging/homebrew/agentry.rb — Tap-Slug, Homepage, Download-URLs
    • packaging/systemd/agentry.service — Documentation=-Feld
    • Dockerfile — Beispiel-Image-Tag im Kommentar (ghcr.io/torben-erz/agentry)

    Doku + Scripts (grep -rn "torben-erz" docs/ scripts/ mkdocs.yml):

    • mkdocs.yml — site_url, repo_url, repo_name, Footer-Link
    • scripts/beta-einladung.md — ~10 URL-Treffer
    • ~30 Markdown-Seiten unter docs/ mit jeweils 1–3 Treffern

    Tests: Tests/agentryTests/{Config,CLI,UpdateNotifier,Ticket}Tests.swift verwenden torben-erz/Agentry als Watch-Target-Fixture. Müssen mitziehen, sonst rote Tests.

    Externe Aktionen:

    • Drei Repos via GitHub-Settings transferieren: Agentry, agentry-dist, homebrew-agentry.
    • Beta-Tester über den Transfer informieren (damit der neue Owner-Name nicht nach Phishing aussieht).
    • Webhook-Konfigurationen in Tester-Repos zeigen weiter auf alten Slug — per Redirect ok, aber neue agentry webhook install-Aufrufe sollten den neuen Owner sehen.

    A.3 Reihenfolge & Aufwand¶

    1. GitHub-Transfer aller drei Repos (3 Klicks pro Repo via Settings → Transfer ownership).
    2. PATs unter <NEW_OWNER> neu ausstellen + im Source-Repo als Action-Secrets eintragen.
    3. Code- und Doku-Sweep mit grep -rn "torben-erz" + Replace.
    4. swift test lokal grün.
    5. .venv-docs/bin/mkdocs build --strict grün.
    6. Test-Release-Tag (z. B. v0.1.0-beta.99) ziehen und verifizieren, dass Tarballs in <NEW_OWNER>/agentry-dist landen und die Formula im neuen Tap aktualisiert wird.
    7. Echtes Release.

    Aufwand: ~2 h Code+Doku, plus ein Verifikations-Release. Keine Migrations-Logik nötig — ~/.agentry/-State bleibt unverändert.

    Teil B — Namens-Wechsel (agentry / Agentry → <NEW_NAME>)¶

    Deutlich aufwändiger als Teil A, weil der Name in fünf qualitativ unterschiedlichen Schichten steckt. Jede Schicht hat andere Implikationen für Bestands-Installationen.

    B.1 Schicht 1 — Swift-Modul + Binary-Name¶

    • Package.swift — name: "agentry" (Package-Name + executable-Target + test-Target dependency)
    • ~30 Test-Dateien mit @testable import agentry

    Effekt für User: Binary heißt nicht mehr agentry, der CLI-Aufruf ändert sich (agentry daemon → <NEW_NAME> daemon). Tap-Formula-Name und alle Service-Templates ziehen das mit.

    B.2 Schicht 2 — Type-Namen mit Agentry-Präfix¶

    • AgentryError (Protocol, ~15 Adopter)
    • AgentryVersion
    • AgentryApp

    Mechanisch via Refactor (Xcode-Rename oder sd/sed) ersetzbar.

    B.3 Schicht 3 — Filesystem-Pfade ~/.agentry/ — kritischste Stelle¶

    grep -rn "\.agentry" Sources/ zeigt die zentralen Stellen:

    • Sources/agentry/Config.swift — fünf Default-Pfade (reposCacheDir, workspaceRoot, stateFile, etagDir, logFile) plus Config-Load-Pfad
    • Sources/agentry/App.swift, Diagnose.swift, InstallID.swift — weitere Hartkodierungen
    • Sources/agentry/CLI.swift — Help-Texte + init-Template, das die Default-Pfade in die generierte config.json schreibt

    Migrations-Entscheidung — Pflicht für Beta-Bestand:

    Beim Daemon-Start prüfen: existiert ~/.agentry/ und ~/.<NEW_NAME>/ nicht → einmaliger mv mit Log-Hinweis. Ohne Migration drohen Doppel-PRs, weil die state.json mit dem processed-Set verloren geht und alle offenen Tickets erneut bearbeitet würden.

    Service-Units referenzieren weiter den alten Pfad — Tester müssen ihre LaunchAgent-/systemd-Unit nach Update neu installieren. Das gehört fett in die Release-Notes.

    B.4 Schicht 4 — Bundle-Identifier + Keychain-Service¶

    • packaging/launchd/com.nanoapes.agentry.plist — Dateiname und Plist-Label
    • Sources/agentry/Config.swift — Beispiel-Identifier in Doc-Kommentar
    • Sources/agentry/Keychain.swift, TokenProvider.swift — Doc-Kommentare
    • docs/features/token-handling.md — tokenKeychainService: "com.nanoapes.agentry" in mehreren Code-Blöcken

    Entkoppelte Frage: ändert sich nanoapes mit (Firmenwechsel) oder bleibt das fix? Wenn nur der Produktname wechselt, wird's com.nanoapes.<new-name>.

    Migrations-Konsequenz — Keychain: Einträge sind an den alten Service-String gebunden. Optionen:

    1. Doppel-Lookup beim Start: erst neuer Service-Name, dann Fallback auf alten. Migration über die Zeit, fühlt sich nahtlos an.
    2. Harter Cut: User müssen Token via security add-generic-password neu eintragen. Im Release-Notes ankündigen.

    Empfehlung: Option 1 für eine Übergangsphase von 1–2 Minor-Versionen, dann Option 2.

    B.5 Schicht 5 — Distribution-Repo-Namen¶

    • agentry-dist → <new-name>-dist
    • homebrew-agentry → homebrew-<new-name> (Homebrew-Konvention: Tap-Repo muss homebrew-<tap-suffix> heißen)

    Beides via GitHub-Transfer + Redirect.

    B.6 Schicht 6 — Doku (~40 Dateien)¶

    grep -rcE "\bagentry\b|\bAgentry\b" zeigt die heavy hitters:

    • docs/features/cli.md (~50)
    • docs/anwendung/troubleshooting.md (~45)
    • docs/features/service-mode.md (~42)
    • README.md (~33)
    • CLAUDE.md (~25)

    Vorsicht: ein großer Teil der Treffer ist Befehlssyntax (z. B. agentry config show in Code-Blöcken). Pures Replace funktioniert mechanisch, aber:

    • Screenshots/Asciinema-Casts mit altem Namen müssen neu aufgenommen werden.

    B.7 Aufwand & Verteilung¶

    Schätzung: 1–2 Personen-Tage.

    Anteil Bereich
    30 % Mechanisches grep+replace (Swift + Doku)
    30 % Migrations-Logik (Pfade, Keychain) inkl. Tests
    20 % Packaging neu (Plist umbenennen, Formula-Template, Service-Unit)
    20 % Verifikation (Release-Tag, Tap-Push, Beta-Tester-Update-Pfad einmal manuell durchspielen)

    Teil C — Wenn beides gleichzeitig¶

    Falls Owner-Wechsel und Namens-Wechsel zusammenfallen (sehr realistisch bei Übergabe an eine Firmen-Org mit eigenem Produktnamen), in einem Schub vor Stufe 1. Die Pain-Points überlappen — CI-Workflow, Homebrew-Formula, Doku-URLs werden ohnehin angefasst.

    Empfohlene Reihenfolge:

    1. Erst Owner-Transfer auf GitHub (3 Klicks pro Repo, Redirects greifen).
    2. Dann Namens-Rename als ein PR mit:
    3. Code-Refactor (Modul, Types, Pfade)
    4. Migrations-Logik (~/.agentry/ → ~/.<NEW_NAME>/, Keychain-Doppel-Lookup)
    5. Packaging-Rename (Plist + Formula + Service-Unit)
    6. Doku-Sweep + .venv-docs/bin/mkdocs build --strict
    7. Release-Workflow auf neue Repo-Namen
    8. Release v0.X.0-rc1 mit dem neuen Namen unter neuem Owner taggen.
    9. Manuelle Update-Probe von einer alten Installation: brew upgrade → Daemon-Start → Migrations-Pfade verifizieren → erstes Ticket verarbeitet.
    10. Beta-Tester benachrichtigen mit klarem Migrations-Hinweis (Service-Unit neu installieren, ggf. Token via Keychain neu eintragen wenn Option 2 gewählt).

    Verifikations-Checkliste¶

    Bevor der Rename als „fertig" gilt:

    • swift test grün (alle Fixtures mit neuem Owner/Namen)
    • .venv-docs/bin/mkdocs build --strict grün
    • grep -rn "torben-erz" (bzw. alter Owner) liefert null Treffer
    • grep -rnE "\bagentry\b|\bAgentry\b" (bzw. alter Name) liefert nur noch erwartete Treffer (Git-Historie, Migrations-Fallback, Doku-Erwähnungen „früher hieß es")
    • Test-Release in der neuen Owner/Name-Konstellation gezogen
    • Tarballs erscheinen in <NEW_OWNER>/<new-name>-dist
    • Formula in homebrew-<new-name> aktualisiert
    • brew upgrade von einer alten Installation durchgespielt
    • ~/.agentry/ → ~/.<NEW_NAME>/-Migration in einer Beta-Test-Umgebung verifiziert
    • Keychain-Token werden weiter gefunden (Fallback-Lookup) ODER Release-Notes weisen klar auf Neu-Eintragung hin
    • Beta-Tester sind informiert (Newsletter / Slack / Discord)
