    Phasen-Historie¶

    Chronologische Auflistung aller abgeschlossenen Entwicklungs-Phasen seit dem Spike. Diese Seite ist das Devlog des Produkts — sie wächst pro Phase und ersetzt den früheren „Erreichte Meilensteine"-Block in CLAUDE.md. Für den aktuellen Stand und die letzten Phasen siehe CLAUDE.md; hier liegt die vollständige Detail-Historie.

    2026-05-10¶

    • Spike: Issue #1 → PR #2 in 2,5 min validiert.
    • Multi-Repo: Watch-Strategien repo / repos / ownerScope konfigurierbar; Default-Branch pro Repo automatisch via gh api.
    • Phase 1 Härtung: ConfigValidator, EnvironmentCheck, AgentryError- Protocol, PipelineFailure mit Phase-Tracking, Timeout pro Agent-Run, CrashRecovery, 42 Unit-Tests.
    • Refactor Issue → Ticket: Domain-Vokabular plattform-neutral für künftige GitLab/Jira-Sources.
    • Doku-Site: MkDocs Material unter docs/, CI baut, kein Auto-Deploy (Privacy bei privatem Repo).
    • Phase 2.1 Log-Persistenz: rotierender File-Sink, Level + Pfad konfigurierbar, parallel zu stdout.
    • Phase 2.2 Health-/Status-Endpoint: swift-nio-basierter HTTP-Server (/healthz, /readyz, /status), Default-Bind 127.0.0.1.
    • Phase 2.3 Metriken: /metrics im Prometheus-Text-Format mit Counter (tickets_processed/succeeded/failed/polling_errors) und Gauges (uptime, ready, last_poll_seconds, poll_interval_seconds, info-Label).
    • Phase 2.4a Sandbox-Plugin-Architektur: SandboxStrategy-Protocol + SandboxRouter mit Label-Override / Rules / Default. Capability- Discovery beim Start.
    • Phase 2.4b LinuxBwrapStrategy: ruft bwrap mit System-RO-Binds (/usr, /etc, /opt), tmpfs für /tmp//var/tmp/$HOME, Workspace
    • HOME-Build-Caches read-write. Namespaces --unshare-pid/uts/ipc (Netz und User-Namespace bewusst nicht — Layer-7-Filter via firewalld, Bare- Cache-UID via Host-User). Options extraReadOnlyBinds und extraWritePaths. Args-Builder als pure-Funktion testbar. linux-container und tart-vm folgen ohne Architektur-Änderung wenn Kunden-Bedarf entsteht.
    • Phase 2.4c MacOSSandboxStrategy: ruft sandbox-exec mit eingebettetem Default-.sb-Profil (deny default für Writes, Allowlist für Workspace, TMP, Build-Caches unter $HOME) oder Custom-Profil via sandbox.strategies."macos-sandbox".profile. Plattform-Check + Tool- Discovery in isAvailable().
    • Phase 2.5 Token-Handling: 3-Quellen-Hierarchie (AGENTRY_GITHUB_TOKEN-Env / tokenFile mit 0600 / gh auth token- Fallback). Token wird einmal resolved und via setenv("GH_TOKEN", …) an alle gh-Subprocesses weitergereicht. Daemon ist ab jetzt nicht mehr zwingend an eine eingeloggte gh-Session gebunden — Voraussetzung für Service-Modus.
    • Phase 3.1 Codex-Backend: CodexBackend als zweite AgentBackend-Implementierung neben ClaudeCodeBackend — ruft codex exec --skip-git-repo-check --full-auto. Prompt-Logik in AgentPromptBuilder zentral, Backends teilen sich Fresh- und Revise- Prompts. Validator-Liste und App.makeAgent kennen claude-code + codex.
    • Phase 3.2 Parallele Ticket-Verarbeitung: Daemon läuft als Producer/Consumer mit AsyncStream<Ticket>-Bridge, Poller speist N Worker parallel. TicketQueue bekommt atomaren claim() (processed ∪ inFlight) als Mutex gegen Doppel-Trigger. DaemonStatus trackt Aktivität pro Worker; /status und /metrics zeigen activeWorkers/maxWorkers. Default maxConcurrency: 1 erhält das alte serielle Verhalten.
    • Phase 3.3 Webhooks: WebhookServer (eigener swift-nio-Server, POST /webhook/github) nimmt GitHub-Events issues.labeled und pull_request.labeled entgegen. HMAC-SHA256-Signatur-Verifizierung via swift-crypto, constant-time-Compare. Secret aus AGENTRY_WEBHOOK_SECRET oder 0600-Datei (webhookSecretFile). Co-Existenz mit Polling über neues TicketIntake — beide Producer (Poller + Webhook) rufen intake.submit(...), das via queue.claim Duplikate ausschließt. Parser auf Webhook-Payload setzt Ticket.trigger direkt aus den head.ref/base.ref-Feldern — kein extra PR-Lookup nötig wie bei Polling. GitLab-Webhook-Mapping folgt bei Bedarf.
    • Phase 3.4 PR-Review-Loop: agent-revise-Label auf PR triggert inkrementellen Revise-Lauf. Ticket.trigger (.fresh / .revise(head, base)) routet im Daemon auf zwei Pipeline-Varianten; Sources pollen ein zweites Endpoint, PullRequestLookup reichert revise-Tickets mit Branch-Paar an. WorkspaceManager checkt Head-Branch via worktree add -B aus, Daemon pusht auf bestehenden Branch ohne PR-Create. Revise- Tickets gehen NICHT in processed (mehrfache Iteration durch Reviewer gewollt) — markCompletedTransient räumt nur inFlight. Status-Labels agent:revising/agent:revised/agent:revise-failed. CrashRecovery handhabt beide Lock-Labels.
    • Phase 3.5 GitLab-Source: provider="gitlab"-Schalter aktiviert GitLabClient (PRIVATE-TOKEN-Auth, gitlab.com oder self-hosted), GitLabSingleProjectSource (REST v4) und GitLabResultReporter (glab CLI). ResultReporter ist jetzt Protocol mit zwei Implementierungen (GitHubResultReporter/GitLabResultReporter). TokenProvider ist parametrisierbar mit .github(...)/.gitlab(...). CrashRecovery überspringt Hanging-Ticket-Cleanup für GitLab (Workspace-Cleanup bleibt). Watch-Format bei GitLab erlaubt mehrstufige Pfade (group/sub/project); ownerScope/repos noch nicht.

    • Phase 3.6 Pro-Ticket-Routing: AgentRouter resolved Backend und Modell pro Ticket via Label-Konvention (agent:backend:<id>, agent:model:<wert>). Sicherheitsmodell ist Allowlist-basiert — Config.agentBackends (optional, default nil = Routing aus) und Config.agentModels (analog). Default-Backend ist immer implizit erlaubt; nicht-erlaubte Label-Werte fallen mit Log-Warning auf den Default zurück (Tickets failen nicht durch zu enge Allowlist). AgentRunOptions bekommt modelOverride — Backends nutzen options.modelOverride ?? self.model als effektives Modell. Daemon hält AgentRouter statt direktes Backend; App.swift instanziiert alle erlaubten Backends einmalig und füttert den Router. Validator prüft Allowlist-Form + Default-Inklusion. 15 neue Tests (Router- Resolve, Allowlist-Validierung).
    • Installations-Kennung: InstallID erzeugt beim ersten Daemon-Start eine zufällige UUID in ~/.agentry/install.id (0600) und liest sie bei allen weiteren Starts unverändert ein. Kein User-Tracking, kein Geheimnis, kein Phone-Home — heute nur lokal geloggt. Folge-Module (Lizenz-Bindung, Opt-In-Telemetrie, Update-Notifier) sollen denselben Wert nutzen, damit historische Daten ab Tag 1 sauber bleiben. Korrupte/manuell zerschossene Datei wird mit Warning regeneriert. 6 Tests (Persistenz, Permissions, Idempotenz, Parent-Verzeichnis, Regeneration).
