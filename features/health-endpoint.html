    Health- & Status-Endpoint¶

    Agentry exponiert einen schmalen HTTP-Endpoint, damit Monitoring-Systeme (systemd, Kubernetes, Prometheus, externes Uptime-Monitoring) den Daemon beobachten können — ohne dass jemand in Logs grepen muss.

    Drei Endpoints¶

    Pfad HTTP-Status Antwort Wofür
    GET /healthz 200 immer ok Liveness — Prozess lebt? Wird der Server erreicht, ist die Antwort 200.
    GET /readyz 200 oder 503 ready / not ready Readiness — Daemon hat Initialisierung abgeschlossen und Polling-Loop ist live.
    GET /status 200 JSON-Snapshot Detaillierter Daemon-Zustand: Uptime, letzter Polling-Zeitpunkt, aktuelle Aktivität, Counter.

    HEAD-Method-Support: Alle Endpoints akzeptieren HEAD zusätzlich zu GET — gleiche Header (inkl. Content-Length), kein Body. Sinnvoll für Load-Balancer und Monitoring-Tools, die nur den Status-Code probieren wollen (z. B. HAProxy, AWS-ELB-Target-Group-Health-Checks, einige Uptime-Robots).

    Beispiel-Antwort von /status¶

    {
  "backend" : "claude-code",
  "currentActivity" : "idle",
  "lastPolledAt" : "2026-05-10T18:01:56Z",
  "pollIntervalSeconds" : 5,
  "ready" : true,
  "startedAt" : "2026-05-10T18:01:50Z",
  "ticketsFailed" : 0,
  "ticketsProcessed" : 0,
  "ticketsSucceeded" : 0,
  "uptimeSeconds" : 6,
  "watch" : "repo:torben-erz/Agentry"
}
    Feld Bedeutung
    ready true sobald die erste Initialisierungsphase durch ist.
    startedAt ISO8601-UTC-Zeitstempel des Daemon-Starts.
    uptimeSeconds Sekunden seit Start.
    lastPolledAt Zeitpunkt des letzten erfolgreichen Polling-Durchlaufs. null wenn noch nicht gepollt wurde.
    currentActivity idle oder processing(<global-id>, phase=<phase>).
    watch Aus Config.watch.description — z. B. repo:owner/name.
    backend Aktiver Agent-Backend-Identifier.
    pollIntervalSeconds Polling-Intervall aus Config.
    ticketsProcessed Kumulativer Counter (Erfolg + Fehler).
    ticketsSucceeded Counter abgeschlossener Tickets.
    ticketsFailed Counter gescheiterter Tickets.

    Konfiguration¶

    {
  "healthEnabled": true,
  "healthHost": "127.0.0.1",
  "healthPort": 8765
}
    Schlüssel Default Bedeutung
    healthEnabled true Endpoint überhaupt starten? Bei false läuft kein HTTP-Server.
    healthHost "127.0.0.1" Bind-Adresse. Default ist nur lokal — das ist kein Versehen, siehe Sicherheits-Abschnitt unten.
    healthPort 8765 TCP-Port (1–65535).

    Sicherheits-Standard¶

    Der Endpoint bindet standardmäßig nur an 127.0.0.1. Damit ist er ausschließlich vom selben Host erreichbar — nicht vom Netzwerk, nicht von außen. Begründung:

    • /status enthält interne Daemon-Info (Watch-Konfiguration, letzter Poll-Zeitpunkt, Backend-Identifier, Counter). Das ist kein Geheimnis, aber auch kein Public-Endpoint.
    • Es gibt aktuell keine Authentifizierung auf dem Endpoint — jeder, der ihn erreicht, sieht alles.

    Wenn du den Endpoint von außen verfügbar machen willst (Monitoring vom Nachbar-Host, Kubernetes-Probe von außerhalb des Pods), setze healthHost auf 0.0.0.0 und lege eine vorgelagerte Authentifizierung an (Reverse-Proxy mit Basic-Auth, Firewall-Regeln, mTLS, Tailscale-Netz, …). Der ConfigValidator gibt eine Warnung aus, wenn 0.0.0.0 aktiv ist.

    Beispiele¶

    curl -s http://127.0.0.1:8765/healthz             # → "ok"
curl -s http://127.0.0.1:8765/readyz              # → "ready" (oder "not ready")
curl -s http://127.0.0.1:8765/status | jq .       # JSON

    while true; do
    if curl -fsS http://127.0.0.1:8765/healthz > /dev/null; then
        echo "$(date -u +%FT%TZ) ok"
    else
        echo "$(date -u +%FT%TZ) DOWN"
    fi
    sleep 30
done

    [Service]
ExecStart=/opt/agentry/bin/agentry
Restart=on-failure
# systemd >= 252:
Type=notify
# Health-Probe extern via curl + ExecCondition / ExecStartPost

    livenessProbe:
  httpGet:
    path: /healthz
    port: 8765
  periodSeconds: 30
readinessProbe:
  httpGet:
    path: /readyz
    port: 8765
  periodSeconds: 10

    Implementierung¶

    • HealthServer.swift — swift-nio-basierter HTTP1-Server, eine EventLoopGroup mit einem Thread.
    • DaemonStatus.swift — Actor mit Snapshot-API. Daemon schreibt, HealthServer liest.
    • Tests: DaemonStatusTests.swift

    Was noch fehlt (Folgeschritte)¶

    • Auth auf dem Endpoint — heute keine, im Loopback akzeptabel, für externe Exposition Pflicht.
    • Histogramm-Metriken für Agent-Run-Dauer, Polling-Latenz — /metrics exportiert heute nur Counter und Gauges.
    • Last-N-Tickets-Liste im Status — bisher nur kumulative Counter, keine letzten N Ergebnisse.
