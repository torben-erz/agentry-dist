    GitLab als zweite Quelle¶

    Neben GitHub kann Agentry auch GitLab überwachen — Single-Project, Multi-Project oder eine ganze Gruppe (inkl. Subgruppen). Gleicher Pipeline- Pfad wie GitHub: nur die REST-API und die CLI (glab statt gh) sind anders.

    Aktivieren¶

    {
  "provider": "gitlab",
  "host": null,
  "watch": { "type": "repo", "value": "group/project" },
  "triggerLabel": "agent-task",
  "reviseLabel": "agent-revise"
}
    Schlüssel Bedeutung
    provider "github" (Default) oder "gitlab". Bestimmt Source, Reporter, Token-Variable.
    host null → gitlab.com. Für selbst-gehostete Instanzen den Hostnamen setzen (z. B. "gitlab.example.com"). Gleicher Schlüssel wie bei GHES — siehe Konfigurations-Referenz.
    watch.value GitLab-Pfad: "group/project" oder "group/subgroup/project" (mehrstufig erlaubt).

    Watch-Formen¶

    Drei Varianten, alle parallel zur GitHub-Seite:

    // Single-Project
{ "watch": { "type": "repo", "value": "group/project" } }

// Multi-Project (mehrere Projekte derselben Instanz)
{ "watch": { "type": "repos", "value": ["g/p1", "g/sub/p2"] } }

// Group-Scope: alle Projekte einer Gruppe (inkl. Subgruppen)
{ "watch": { "type": "ownerScope", "value": "my-group" } }
{ "watch": { "type": "ownerScope", "value": "my-group/sub" } }

    Group-Scope nutzt GET /groups/<id>/{issues,merge_requests} und holt den Projekt-Pfad pro Treffer aus references.full.

    Funktionsumfang¶

    Feature GitHub GitLab
    Single-Repo/Project-Polling ✅ repo ✅ repo
    Multi-Repo/Project ✅ repos ✅ repos
    Owner-/Group-Scope ✅ ownerScope ✅ ownerScope (mehrstufig)
    Fresh-Pipeline (Issue → MR/PR) ✅ ✅
    Revise-Loop (agent-revise auf MR/PR) ✅ ✅
    Webhook-Empfang ✅ /webhook/github (HMAC) ✅ /webhook/gitlab (Plain-Token)
    Crash-Recovery via API (Label-Cleanup) ✅ ✅

    Voraussetzungen¶

    • glab im PATH — brew install glab oder GitLabs offizielle Builds.
    • GitLab-Token mit den Scopes api, read_repository, write_repository. Wird aus einer dieser drei Quellen gezogen (in dieser Reihenfolge):
    • Environment-Variable AGENTRY_GITLAB_TOKEN
    • tokenFile (0600-Datei)
    • glab auth token als Fallback
    • git mit glab als Credential-Helper — der Daemon richtet das beim Start automatisch für den konfigurierten host ein: git config --global credential.https://<host>.helper '!glab auth git-credential'. Idempotent — wer den Helper schon manuell gesetzt hat, wird nicht überschrieben (gleicher Wert).
    • GITLAB_TOKEN im Prozess-Env — der Daemon setzt das beim Start aus dem aufgelösten Token. glab nutzt das automatisch.

    Architektur¶

    sequenceDiagram
    autonumber
    participant Daemon
    participant Source as GitLabSingleProjectSource
    participant Client as GitLabClient
    participant API as GitLab REST v4
    participant Reporter as GitLabResultReporter
    participant glab

    Daemon->>Source: pollOnce()
    Source->>Client: GET /projects/<encoded>/issues?labels=agent-task
    Client->>API: PRIVATE-TOKEN: …
    API-->>Client: 200 + ETag oder 304
    Client-->>Source: GitLabIssue[]
    Source->>Client: GET /projects/<encoded>/merge_requests?labels=agent-revise
    Client-->>Source: GitLabMergeRequest[]
    Source-->>Daemon: [Ticket] (trigger: .fresh oder .revise)

    Note over Daemon: Pipeline läuft normal — Workspace,<br/>Agent, Commit, Push.

    Daemon->>Reporter: createPullRequest(for: ticket, …)
    Reporter->>glab: glab mr create --source-branch ...
    Reporter->>glab: glab issue note --message ... (oder mr note bei Revise)
    Reporter->>glab: glab issue update --label agent:done --unlabel agent:in-progress

    Das Mapping vom GitLab-Schema zum plattform-neutralen Ticket lebt in GitLabIssue.toTicket(project:) und GitLabMergeRequest.toTicket(project:). Der Reporter unterscheidet anhand ticket.isPullRequest zwischen glab issue … und glab mr … — Issues und MRs leben bei GitLab auf getrennten Endpoints und CLI-Pfaden.

    Webhooks (Echtzeit-Trigger)¶

    Statt zu pollen, kann GitLab Events direkt an Agentry pushen:

    {
  "provider": "gitlab",
  "webhookEnabled": true,
  "webhookHost": "0.0.0.0",
  "webhookPort": 8766,
  "webhookSecretFile": "~/.agentry/webhook-secret"
}
    • Endpoint: POST /webhook/gitlab.
    • Authentifizierung: GitLab schickt einen Plain-Token im X-Gitlab-Token- Header. Wir vergleichen timing-resistent gegen das konfigurierte Secret (constant-time-equals). HMAC wäre stärker; GitLab unterstützt Token-only — deshalb ist HTTPS via Reverse-Proxy doppelt wichtig.
    • Replay-Schutz: X-Gitlab-Event-UUID wird im WebhookDeliveryStore 24 h getrackt. Wiederholungen werden mit 200 OK replay: <uuid> quittiert.
    • Events: Issue Hook (Trigger-Label) und Merge Request Hook (Revise-Label). Wir prüfen changes.labels und triggern nur, wenn das Label neu hinzu- gekommen ist — sonst feuert jeder Edit das Event.

    Im GitLab-Projekt unter Settings → Webhooks anlegen:

    • URL: https://<dein-host>/webhook/gitlab
    • Secret token: Wert aus deiner webhookSecretFile
    • Trigger: Issues events + Merge request events

    Status-Labels¶

    Die Status-Labels (agent:in-progress, agent:done, agent:failed, agent:revising, agent:revised, agent:revise-failed) sind identisch zwischen GitHub und GitLab — die Domänensprache ist plattform-übergreifend einheitlich.

    Beim Setup eines neuen GitLab-Projekts müssen die Labels einmalig angelegt werden:

    PROJECT="group/project"
for label in agent-task agent-revise agent:in-progress agent:done agent:failed agent:revising agent:revised agent:revise-failed; do
  glab label create -R "$PROJECT" --name "$label"
done

    Crash-Recovery¶

    Wie bei GitHub: beim Daemon-Start räumt Agentry hängende Tickets mit agent:in-progress oder agent:revising auf. Bei GitLab läuft das über den GitLabHangingTicketFinder, der je nach Watch-Form pro Projekt oder über das Gruppen-Endpoint Issues/MRs holt und sie auf agent:failed bzw. agent:revise-failed umlabelt — inkl. erklärendem Kommentar.
