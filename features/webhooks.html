    Webhooks (Echtzeit-Trigger)¶

    Neben Polling kann Agentry GitHub- oder GitLab-Webhooks direkt entgegennehmen. Ergebnis: statt 1–5 s Polling-Latenz reagiert der Daemon innerhalb von Millisekunden, und Polling-Quota geht runter.

    Status: Beide Provider werden unterstützt — POST /webhook/github (HMAC-SHA256) und POST /webhook/gitlab (Plain-Token). Der WebhookServer exponiert genau die Route, die zum konfigurierten provider passt.

    Aktivieren¶

    {
  "webhookEnabled": true,
  "webhookHost": "0.0.0.0",
  "webhookPort": 8766,
  "webhookSecretFile": null
}

    Plus: das Webhook-Secret muss als Environment-Variable gesetzt sein:

    export AGENTRY_WEBHOOK_SECRET="$(openssl rand -hex 32)"

    Oder als 0600-Datei via webhookSecretFile. Ohne Secret startet der Server nicht — Agentry weigert sich, ungeprüfte Requests anzunehmen.

    Schlüssel Default Bedeutung
    webhookEnabled false Wenn true, startet zusätzlich zum Polling ein HTTP-Server.
    webhookHost "127.0.0.1" Bind-Adresse. Für echten Webhook-Empfang 0.0.0.0 + Reverse-Proxy davor.
    webhookPort 8766 TCP-Port. Muss sich vom healthPort unterscheiden — Validator weist Kollision ab.
    webhookSecretFile null Optional, Pfad zu einer 0600-Datei. Wenn null UND AGENTRY_WEBHOOK_SECRET unset: Server startet nicht.

    Architektur¶

    sequenceDiagram
    autonumber
    participant U as Reviewer / User
    participant GH as GitHub
    participant LB as Reverse-Proxy<br/>(TLS)
    participant WS as WebhookServer
    participant V as Signature-Verifier
    participant D as Decoder
    participant I as TicketIntake
    participant W as Worker

    U->>GH: Setzt Label agent-task / agent-revise
    GH->>LB: POST /webhook/github<br/>+ X-Hub-Signature-256
    LB->>WS: POST (HTTP, Loopback)
    WS->>V: HMAC-SHA256(body, secret)
    V-->>WS: ok
    WS->>D: decode(event, body)
    D-->>WS: Ticket (fresh / revise)
    WS->>I: submit(ticket)
    I->>I: queue.claim → true
    I-->>WS: accepted
    WS-->>GH: 202 Accepted
    I->>W: Ticket im Stream
    W->>W: Pipeline wie gehabt

    Wichtige Eigenschaften:

    • Co-Existenz mit Polling. Beide Producer (Poller + WebhookServer) rufen TicketIntake.submit. TicketQueue.claim ist atomar und schließt Duplikate aus. Polling bleibt als Fallback aktiv — wenn ein Webhook verloren geht, fängt der nächste Poll-Tick es.
    • Signature- / Token-Verifizierung. Jeder Request muss authentifiziert sein:
    • GitHub: HMAC-SHA256-Signatur im Header X-Hub-Signature-256. Constant-time-Vergleich via swift-crypto.
    • GitLab: Plain-Token im Header X-Gitlab-Token. Constant-time- Vergleich gegen das konfigurierte Secret.
    • Pull-Branch-Lookup entfällt. Bei Polling muss der GitHub-Daemon pro Revise-PR einen extra GET /pulls/<n>-Call machen, um Head- und Base- Branch zu bekommen. Im Webhook-Payload sind die Branches direkt enthalten — keine zusätzliche API-Last. Bei GitLab liefert bereits das MR-Polling die Branches mit.

    Replay-Schutz via Delivery-ID¶

    Beide Plattformen schicken pro Lieferung eine UUID:

    • GitHub: X-GitHub-Delivery.
    • GitLab: X-Gitlab-Event-UUID.

    Bei Empfangsfehlern liefert GitHub bis zu 8× über 24 h nach — mit identischer Delivery-ID; GitLab verhält sich vergleichbar. Wir nutzen das, um Replay-Versuche abzufangen.

    Der WebhookDeliveryStore (Actor, in-memory) merkt sich gesehene Delivery-IDs für 24 h (TTL konfigurierbar im Init). Trifft eine zweite Anfrage mit derselben ID ein:

    • Antwort: 200 OK mit Body replay: <id>.
    • Log: Webhook: Replay erkannt (delivery=<id>) — verworfen.
    • Kein Decoder-Aufruf, kein intake.submit.

    Drei Verteidigungslinien zusammen:

    1. Signatur/Token — HMAC-SHA256 bei GitHub (schützt zusätzlich vor Body-Manipulation), Plain-Token bei GitLab (schwächer; TLS via Reverse-Proxy ist deshalb besonders wichtig).
    2. Delivery-ID-Tracking — schützt vor exakt-Wiederholung in 24 h.
    3. TicketQueue.claim — schützt vor Doppelverarbeitung desselben Tickets.

    Der Store ist bewusst in-memory: nach Daemon-Restart fängt das Tracking bei null an. Das schützt operativ einfach (kein Disk-State zu verwalten); die anderen zwei Linien greifen in der Zeit weiter. Lazy-Cleanup beim nächsten recordIfNew-Call hält die Map kompakt.

    Response-Codes¶

    Status Bedeutung
    202 Accepted Signatur valide, Ticket wurde aufgenommen.
    200 OK Signatur valide, aber Event/Action/Label nicht relevant, Ticket war Duplikat, oder Replay erkannt.
    400 Bad Request Body konnte nicht geparst werden.
    401 Unauthorized Signatur fehlt oder ist ungültig.
    404 Not Found Pfad ist nicht /webhook/github bzw. /webhook/gitlab (passend zum Provider).
    405 Method Not Allowed Andere Methode als POST.

    Auto-Setup (empfohlen)¶

    Statt durch die UI zu klicken: Agentry kann Webhooks selbst anlegen, provider-agnostisch via gh api / glab api.

    # GitHub
agentry webhook install --url https://agentry.example.com/webhook/github

# GitLab
agentry webhook install --url https://agentry.example.com/webhook/gitlab

# Plan anzeigen ohne API-Aufruf
agentry webhook install --url https://x/webhook/github --dry-run

    Voraussetzung: gh/glab ist im PATH und eingeloggt, und das Webhook-Secret ist via AGENTRY_WEBHOOK_SECRET oder webhookSecretFile verfügbar. Idempotent — vorhandene Hooks mit derselben URL werden nicht zweimal eingetragen.

    Weitere Subcommands: agentry webhook list, agentry webhook delete <id>. Details: CLI-Subcommands.

    Manuelles Setup auf GitHub-Seite¶

    1. Im Ziel-Repo unter Settings → Webhooks → Add webhook anlegen.
    2. Payload URL: https://<dein-host>/webhook/github.
    3. Content type: application/json.
    4. Secret: identischer Wert wie AGENTRY_WEBHOOK_SECRET im Daemon-Env.
    5. Events: „Let me select individual events" → Issues und Pull requests.
    6. Speichern. GitHub schickt einen ping-Event, den der Server höflich mit 200 ignored: ping quittiert.

    Manuelles Setup auf GitLab-Seite¶

    (Die meisten greifen zu agentry webhook install, oben — manuell-Pfad zur Vollständigkeit.)

    1. Im Ziel-Projekt unter Settings → Webhooks anlegen (oder für Group-Scope unter Group Settings → Webhooks).
    2. URL: https://<dein-host>/webhook/gitlab.
    3. Secret token: identischer Wert wie AGENTRY_WEBHOOK_SECRET im Daemon-Env (bzw. der Inhalt der webhookSecretFile).
    4. Trigger: Issues events und Merge request events aktivieren.
    5. Speichern und „Test → Issues Hook" — der Server quittiert mit 200 ignored: ..., wenn das Test-Event nicht zufällig ein Label-Add ist.

    GitLab triggert sein Issue/MR-Webhook-Event auf jede Änderung — der Decoder schaut deshalb in changes.labels, um einen Label-Add von einem beliebigen Edit zu unterscheiden. Erst wenn das Trigger- bzw. Revise-Label neu hinzugekommen ist, geht ein Ticket in den Intake.

    TLS und öffentlicher Empfang¶

    Der Daemon terminiert kein TLS selbst — das ist Aufgabe eines Reverse-Proxys (nginx, Caddy, Cloud-Load-Balancer). Setup minimal:

    server {
    listen 443 ssl http2;
    server_name webhook.example.com;
    ssl_certificate     /etc/letsencrypt/.../fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/.../privkey.pem;

    location /webhook/github {
        proxy_pass http://127.0.0.1:8766;
        proxy_set_header X-Hub-Signature-256 $http_x_hub_signature_256;
        proxy_set_header X-GitHub-Event $http_x_github_event;
    }
}

    Der Webhook-Server kann auch direkt auf 0.0.0.0 binden, ohne Reverse-Proxy — GitHub akzeptiert auch http:// als Payload-URL. Davon ausdrücklich abraten in der Praxis: das Secret reicht über die Leitung, der Body ebenfalls. TLS ist Pflicht für produktiven Betrieb.
