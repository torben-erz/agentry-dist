    Sandbox für Agent-Ausführung¶

    Agentry kann den Agent-Aufruf in einer Sandbox isolieren — damit ein manipuliertes Issue (Prompt-Injection) keinen Schaden außerhalb seines Worktrees anrichten kann. Welche Sandbox greift, ist pro Ticket konfigurierbar.

    Status¶

    Phase 2.4 abgeschlossen: Plugin-Architektur, MacOSSandboxStrategy (sandbox-exec mit Default-.sb-Profil) und LinuxBwrapStrategy (bwrap mit Namespaces + tmpfs) sind live. Auf macOS und Linux läuft der Agent automatisch in einer plattform-passenden Sandbox, sobald sandbox.default auf die jeweilige Strategie gesetzt ist.

    Container (linux-container via Docker/Podman) und VM-Isolation (tart-vm auf macOS Apple Silicon) bleiben optionale Folge-Phasen — kommen, wenn ein konkreter Kundenbedarf sie rechtfertigt.

    Verfügbare Strategien¶

    Strategie Plattform Wofür Status
    none beide Dev-Setups, vertrauenswürdige On-Prem-Umgebungen ✅ Verfügbar
    macos-sandbox macOS iOS/macOS-App-Tickets, Prozess-Sandbox via .sb-Profil ✅ Verfügbar (2.4c)
    linux-bwrap Linux Web/Backend-Tickets auf Linux-Server, leichtgewichtige Prozess-/Mount-Isolation ✅ Verfügbar (2.4b)
    linux-container beide Cross-Platform-Linux-Workloads, Docker/Podman 🟡 Stub-Architektur vorhanden, Implementierung wenn Kunde es braucht
    tart-vm macOS Apple Silicon iOS/macOS in voller VM-Isolation, ideal für SaaS-Mac-Pool 🟡 Stub-Architektur vorhanden — Apple-2-VM-Limit pro Host beachten, Alternativen

    Jede Strategie implementiert SandboxStrategy mit:

    • identifier — wird in Config und Labels referenziert
    • humanName — fürs Logging
    • availabilityHint — Setup-Tipp für den Operator
    • isAvailable() — Capability-Discovery beim Daemon-Start
    • run(...) — der eigentliche Sandbox-Aufruf

    Welcher Setup passt zu wem?¶

    Dein Setup Empfehlung
    Du selbst (macOS, baust iOS/macOS/visionOS/iPadOS) default: "macos-sandbox", optional Regel agent:platform:linux → linux-container falls du auch Web/Backend hast
    Kunde A (Linux-Server, kein iOS) default: "linux-bwrap" (oder linux-container). Tickets mit agent:platform:ios werden abgelehnt mit Meldung „dieser Daemon läuft auf Linux".
    Kunde B (Mac-Mini, gemischte Tickets) default: "linux-container" für Web/Backend, rules routen iOS auf macos-sandbox
    Kunde C (SaaS, gemischter Mac/Linux-Pool) Mehrere Daemon-Instanzen, je nach Plattform mit eigener Default-Strategie. Routing entscheidet welcher Daemon ein Ticket bekommt (Phase 5+).

    Konfiguration¶

    {
  "sandbox": {
    "default": "linux-bwrap",
    "strategies": {
      "macos-sandbox":   { "profile": "/etc/agentry/agent.sb" },
      "linux-container": { "engine": "podman", "image": "agentry/builder:1.0" }
    },
    "rules": [
      { "ifLabel": "agent:platform:ios", "use": "macos-sandbox" },
      { "ifLabel": "agent:platform:web", "use": "linux-container" }
    ]
  }
}
    Feld Bedeutung
    default Strategy-Identifier, der greift, wenn weder Label-Override noch Regel matched. Plattform-Default: "macos-sandbox" auf macOS, "linux-bwrap" auf Linux, "none" auf unbekannten Plattformen. Out-of-the-box läuft der Daemon gesandboxed; auf Linux ist bubblewrap (bwrap) Voraussetzung — fehlt es, startet der Daemon mit SandboxError.defaultUnavailable statt still ungeschützt zu laufen. Wer explizit ohne Schutz starten will: "default": "none".
    strategies Pro Strategie ein Options-Bag (String→String). Inhalt ist strategie-spezifisch; unbekannte Schlüssel werden ignoriert.
    rules Liste von { ifLabel, use }-Objekten. Erste matchende Regel gewinnt — Reihenfolge zählt.

    Auswahl-Reihenfolge pro Ticket¶

    flowchart TB
    T[Ticket eingegangen] --> O{Label<br/>agent:sandbox:&lt;name&gt;<br/>vorhanden?}
    O -->|ja| OS[Strategie aus Label-Override]
    O -->|nein| R{Erste matchende<br/>Rule?}
    R -->|ja| RS[Strategie aus Rule.use]
    R -->|nein| D[Strategie aus<br/>sandbox.default]

    OS --> X[Strategie registriert<br/>+ verfügbar?]
    RS --> X
    D --> X

    X -->|ja| RUN[Agent läuft<br/>in dieser Sandbox]
    X -->|nein| FAIL[Ticket scheitert<br/>mit klarer Meldung]
    1. Explizites Label agent:sandbox:<name> am Ticket (höchste Priorität) — Reviewer-/Operator-Override pro Einzelfall.
    2. Erste matchende Regel aus sandbox.rules. Deterministisch nach Reihenfolge.
    3. sandbox.default aus der Config.

    Wenn die gewählte Strategie nicht registriert ist, wirft der Router — Sicherheit darf nicht stillschweigend auf none zurückfallen.

    Capability-Discovery beim Start¶

    Pro registrierter Strategie wird isAvailable() aufgerufen. Beispiel-Log (macOS, Default-Sandbox macos-sandbox):

    [INFO] Sandbox 'macos-sandbox' (macOS sandbox-exec) — verfügbar. (Default — wird ohne Label-Override genutzt)
[INFO] Sandbox 'none' (Keine Sandbox) — verfügbar. (registriert für Label-Override / Routing-Regeln)

    Die Default-Strategie wird in derselben Zeile als solche markiert, damit der Operator nicht raten muss, welche der „verfügbar"-Zeilen die aktive ist. Alle anderen verfügbaren Strategien sind als Fallback für Label-Override (agent:sandbox:<name>) oder sandbox.rules registriert.

    Plattform-inkompatible Strategien (z. B. linux-bwrap auf macOS, macos-sandbox auf Linux) werden nur auf DEBUG-Level geloggt und nicht als „nicht verfügbar" markiert — der Operator hat keinen Setup-Pfad, der sie hier verfügbar machen würde, ein WARN wäre nur Lärm.

    Wenn ein Tool fehlt, aber die Strategie prinzipiell auf der Plattform laufen würde (z. B. linux-bwrap auf Linux ohne installiertes bubblewrap), kommt ein echtes WARN mit Installations-Hinweis:

    [WARN] Sandbox 'tart-vm' (Tart macOS-VM) — nicht verfügbar.
        Hinweis: 'tart' muss installiert sein (`brew install cirruslabs/cli/tart`).

    Wenn die default-Strategie auf diesem Host nicht verfügbar ist, scheitert der Daemon beim Start mit klarer Meldung statt unbemerkt ohne Sandbox zu laufen.

    Per-Ticket-Override via Label¶

    Operator/Reviewer kann pro Ticket eine andere Strategie wählen:

    gh issue create -R <repo> \
    --title "Spezial-Aufgabe" \
    --body "…" \
    --label "agent-task" \
    --label "agent:sandbox:linux-container"

    Damit greift linux-container für genau dieses Ticket — unabhängig von Default und Regeln.

    Vertriebsmodell-Implikationen¶

    Modell iOS-Tickets Was nötig
    On-Prem auf Linux-Server ❌ Tickets mit agent:platform:ios ablehnen mit klarer Meldung
    On-Prem auf Mac-Mini ✅ macos-sandbox oder tart-vm als Sandbox
    SaaS (cloud) ✅ Mac-Pool (EC2 Mac/MacStadium) für iOS-Worker, x86 für Rest
    Hybrid (Cloud-Frontend, On-Prem-Worker) ✅ wenn Kunde Mac-Hardware hat Worker entscheidet lokal nach Plattform

    Erweitern um eine neue Strategie¶

    1. Datei anlegen: Sources/agentry/Sandbox/<Name>Strategy.swift
    2. SandboxStrategy adoptieren — identifier, humanName, availabilityHint, isAvailable() und run(...) implementieren.
    3. In App.main() zur Strategy-Liste hinzufügen (aktuell hartkodiert, Strategy-Factory ist Folge-Schritt). Sub-Optionen aus config.sandbox.strategies[<identifier>] als [String: String] lesen.
    4. Optional Validator erweitern, wenn Sub-Optionen geprüft werden müssen.
    5. Doku: in dieser Datei in der „Verfügbare Strategien"-Tabelle den Status auf ✅ heben und Setup-Details ergänzen.

    macos-sandbox im Detail¶

    Was die Default-Sandbox erlaubt¶

    MacOSSandboxStrategy ruft sandbox-exec mit einem eingebetteten .sb- Profil auf. Modell: deny default für Filesystem-Writes, Allowlist nur für gezielte Pfade:

    Schreibzugriff erlaubt Begründung
    (param "WORKSPACE") — der Worktree des Tickets Der Agent muss am Code arbeiten.
    (param "TMP") + /private/var/folders Build-Tools schreiben hierher (Xcode-DerivedData, SwiftPM-Builds, npm-Tarballs, …).
    ~/Library/Caches, ~/Library/Developer, ~/Library/Logs Xcode-Caches, SDK-Index, Build-Logs.
    ~/.swiftpm, ~/.cache, ~/.npm, ~/.yarn, ~/.bun, ~/.pnpm-store, ~/.gradle, ~/.cocoapods, ~/.cargo, ~/.rustup, ~/.local Paket-Manager-Caches verschiedener Sprachen.
    ~/.claude Claude-Code-eigener State (Project-Logs, etc.).

    Lesezugriff ist global erlaubt — Read-Isolation auf macOS wäre Job einer VM-Strategie. Netzwerk-Outbound ist offen; Host-Filterung übernimmt linux-bwrap oder ein Container.

    Was die Default-Sandbox verbietet¶

    Implizit über deny default → alles, was nicht in der Allowlist steht. Konkret damit gesperrt für Schreibvorgänge:

    • /etc, /usr, /System, /Library — System-Konfiguration
    • ~/.ssh, ~/.aws, ~/.gnupg, ~/.gitconfig, ~/.netrc — Credentials
    • ~/.config, ~/.bash_history, ~/.zsh_history — Shell-State
    • Alle anderen $HOME-Pfade außerhalb der Allowlist

    Eigenes Profil verwenden¶

    Wenn dir die Default-Allowlist zu liberal oder zu eng ist, setze sandbox.strategies.macos-sandbox.profile auf einen eigenen .sb-Pfad:

    {
  "sandbox": {
    "default": "macos-sandbox",
    "strategies": {
      "macos-sandbox": { "profile": "/etc/agentry/agent.sb" }
    }
  }
}

    sandbox-exec substituiert beim Lesen des Profils die Parameter WORKSPACE, TMP, HOME per -D — du kannst sie also in deinem Profil wie im Default referenzieren ((param "WORKSPACE")).

    Bekannte Trade-offs¶

    • sandbox-exec ist seit Jahren „deprecated", in der Praxis aber stabiler Bestandteil von macOS. Sollte Apple das Tool wirklich entfernen, übernimmt eine TartVMStrategy für volle Isolation.
    • Netzwerk-Filterung ist mit sandbox-exec nur grob möglich. Wenn das ein Sicherheits-Anforderung deines Setups ist, fahre linux-bwrap oder einen Container statt macos-sandbox.
    • Xcode-Builds funktionieren, weil Caches und DerivedData in der Allowlist stehen. Tools, die woanders schreiben wollen, scheitern mit „Operation not permitted" — Lösung ist dann ein erweitertes Custom-Profil.

    linux-bwrap im Detail¶

    Setup auf dem Host¶

    # Debian / Ubuntu
sudo apt install bubblewrap

# Fedora / RHEL / Rocky
sudo dnf install bubblewrap

# Arch
sudo pacman -S bubblewrap

    bwrap muss entweder setuid-root installiert sein (Debian/Ubuntu- Default) oder der Kernel muss kernel.unprivileged_userns_clone=1 gesetzt haben. Andernfalls scheitert der Aufruf mit „setting up uid map: Permission denied".

    Was die Default-Sandbox tut¶

    Beim Agent-Aufruf öffnet der Daemon einen neuen Mount-/PID-/UTS-/IPC- Namespace und mountet folgendes Bild hinein:

    Pfad Modus Begründung
    /usr, /etc, /opt (wenn vorhanden) read-only System-Binaries und -Configs für git, claude, Build-Tools.
    /lib, /lib64, /bin, /sbin symlink → /usr/... Standardlayout auf modernen Distros (usr-merge).
    /proc, /dev Pseudo-FS Damit Prozesse /proc/self und Basis-Geräte finden.
    /tmp, /var/tmp frischer tmpfs Isolierte Scratch-Verzeichnisse.
    Workspace (cwd) read-write Hier arbeitet der Agent.
    $HOME tmpfs (leer) Sauberes Home — Default-Konfig-Dateien wirken nicht hinein.
    $HOME/.claude, $HOME/.cache, $HOME/.config, $HOME/.swiftpm, $HOME/.npm, $HOME/.yarn, $HOME/.bun, $HOME/.pnpm-store, $HOME/.gradle, $HOME/.cocoapods, $HOME/.cargo, $HOME/.rustup, $HOME/.local read-write (wenn am Host vorhanden) Build-Caches und Auth-State werden durchgereicht — fehlen sie am Host, werden sie nicht ge-mountet.

    Zusätzlich werden Namespaces isoliert (--unshare-pid, --unshare-uts, --unshare-ipc) und der Prozess stirbt mit dem Daemon (--die-with-parent).

    Was die Default-Sandbox NICHT tut¶

    • Kein Network-Isolat — der Sandbox-Prozess teilt den Netzwerk- Namespace des Hosts. Wenn du Outbound-Traffic einschränken willst, setze das vor dem Daemon mit nftables/firewalld/slirp4netns um oder wechsle auf eine Container-Strategie.
    • Kein User-Namespace (--unshare-user ist deaktiviert) — damit bleibt der Daemon-User im selben UID-Kontext und das Bare-Cache-Repo funktioniert ohne UID-Mapping.
    • Keine Filterung des /host-Filesystems außerhalb der gemounteten Pfade — alles, was nicht explizit gemountet ist, existiert in der Sandbox schlicht nicht.

    Eigene Pfade zusätzlich mounten¶

    Wenn du repo-spezifische Tool-Pfade brauchst, ergänze die Sub-Optionen:

    {
  "sandbox": {
    "default": "linux-bwrap",
    "strategies": {
      "linux-bwrap": {
        "extraReadOnlyBinds": "/opt/android-sdk, /opt/llvm",
        "extraWritePaths": "/var/agentry/buildcache"
      }
    }
  }
}
    Schlüssel Wirkung
    extraReadOnlyBinds Komma-separierte Pfade, zusätzlich read-only ge-mountet (--ro-bind).
    extraWritePaths Komma-separierte Pfade, zusätzlich read-write ge-mountet (--bind).
