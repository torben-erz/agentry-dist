    Service-Modus (launchd / systemd)¶

    Im Produktionsbetrieb soll der Daemon nicht in einem Terminal-Fenster laufen, sondern als systemnaher Hintergrund-Dienst mit Auto-Restart und Boot-Start. Agentry liefert dafür Templates unter packaging/, die für deine Maschine substituiert werden.

    Was bedeutet 'Service-Modus' hier?

    Agentry läuft im Service-Modus mit derselben Binary und derselben Config wie im Terminal — der Unterschied ist nur, wer den Prozess startet und überwacht (launchd auf macOS, systemd auf Linux). Der agentry-CLI bleibt unverändert für Setup, Validierung und Status-Abfrage.

    macOS — LaunchAgent¶

    User-Agents laufen im Login-Kontext des Operators und brauchen kein root — das ist der empfohlene Standard.

    1. Binary platzieren¶

    # Release-Build erzeugen und an einen stabilen Pfad legen:
swift build -c release
sudo cp .build/release/agentry /usr/local/bin/agentry
sudo chmod +x /usr/local/bin/agentry

    agentry muss aus dem PATH heraus aufrufbar sein, sonst kann der LaunchAgent ihn beim Start nicht finden.

    2. Plist substituieren¶

    # In ein neues Arbeitsverzeichnis kopieren:
mkdir -p ~/Library/LaunchAgents
cp packaging/launchd/com.nanoapes.agentry.plist \
   ~/Library/LaunchAgents/com.nanoapes.agentry.plist

# Platzhalter ersetzen:
sed -i '' \
  -e "s|__AGENTRY_BIN__|/usr/local/bin/agentry|g" \
  -e "s|__HOME__|$HOME|g" \
  ~/Library/LaunchAgents/com.nanoapes.agentry.plist

    3. Aktivieren¶

    # In den User-Domain laden, aktivieren, starten:
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.nanoapes.agentry.plist
launchctl enable    gui/$(id -u)/com.nanoapes.agentry
launchctl kickstart -k gui/$(id -u)/com.nanoapes.agentry

# Status prüfen:
launchctl print gui/$(id -u)/com.nanoapes.agentry | head -40

    4. Sichten¶

    # Schneller Health-Check (gleiche Logik wie `curl /status`):
agentry status

# Live-Logs aus der rotierenden Datei:
agentry logs -f

# launchd-Stdout (für "kommt nicht hoch"-Fälle):
tail -f ~/.agentry/launchd-stderr.log

    Entladen¶

    launchctl bootout gui/$(id -u)/com.nanoapes.agentry

    Linux — systemd User-Service¶

    User-Services brauchen kein root und sind die einfachste Form. Für Multi-User-Maschinen siehe weiter unten den Abschnitt zum System-Service.

    1. Binary platzieren¶

    swift build -c release
mkdir -p ~/.local/bin
cp .build/release/agentry ~/.local/bin/agentry
chmod +x ~/.local/bin/agentry

    Stelle sicher, dass ~/.local/bin im PATH deiner Shell ist.

    2. Unit substituieren¶

    mkdir -p ~/.config/systemd/user
cp packaging/systemd/agentry.service ~/.config/systemd/user/agentry.service

sed -i \
  "s|__AGENTRY_BIN__|$HOME/.local/bin/agentry|g" \
  ~/.config/systemd/user/agentry.service

    3. Aktivieren¶

    systemctl --user daemon-reload
systemctl --user enable --now agentry.service

systemctl --user status agentry

    Lingering aktivieren

    Damit der Service auch ohne aktiven Login (z. B. nach Boot) läuft: 

    sudo loginctl enable-linger $USER

    4. Logs¶

    systemd schickt stdout/stderr ins journald. Beide Quellen sind verfügbar:

    # Über journald (alle Levels mit Service-Filter):
journalctl --user -u agentry -f

# Über die rotierende Agentry-Datei (gleiche Einträge):
agentry logs -f

    Stoppen / Deaktivieren¶

    systemctl --user stop agentry
systemctl --user disable agentry

    Linux — System-Service (Multi-User-Server)¶

    Wenn der Daemon nicht an einen Login gebunden sein soll (z. B. auf einem Headless-Server), lege die Unit unter /etc/systemd/system/ ab und setze explizit User=, damit der Daemon nicht als root läuft:

    sudo cp packaging/systemd/agentry.service /etc/systemd/system/
sudo sed -i \
  -e "s|__AGENTRY_BIN__|/usr/local/bin/agentry|g" \
  -e 's|^; User=__USER__|User=agentry|' \
  -e 's|^; Group=__USER__|Group=agentry|' \
  -e 's|^; WorkingDirectory=/home/__USER__|WorkingDirectory=/home/agentry|' \
  /etc/systemd/system/agentry.service

# Dedizierten Service-Account anlegen (mit Home für ~/.agentry):
sudo useradd --system --create-home --shell /usr/sbin/nologin agentry

sudo systemctl daemon-reload
sudo systemctl enable --now agentry

    Für die Health-Checks musst du agentry status als agentry-User aufrufen (oder per --url einen expliziten Endpoint angeben), weil die Config-Suche im Home-Verzeichnis des aufrufenden Users stattfindet.

    Härtung¶

    Die mitgelieferte systemd-Unit enthält kommentierte Härtungs-Schalter (ProtectSystem, ProtectHome, NoNewPrivileges, PrivateTmp). Für System-Services empfohlen, für User-Services in Ordnung wegzulassen. Auf macOS übernimmt das Sandbox-Modul des Daemons selbst die Härtung des Agent-Prozesses — siehe Sandbox.

    Was die Templates nicht automatisch erledigen¶

    • Config-Anlage — agentry init einmal ausführen, bevor der Service startet.
    • Token-Bereitstellung — AGENTRY_GITHUB_TOKEN als Env in der Unit oder tokenFile in der Agentry-Config setzen. Direkter Klartext-Eintrag in Plist/Service-Datei nicht empfehlenswert.
    • Webhook-Reverse-Proxy — wenn webhookEnabled=true und der Endpoint nach außen erreichbar sein soll, brauchst du einen Reverse-Proxy mit TLS (nginx/Caddy). Der Daemon bindet bewusst auf 127.0.0.1.

    Distribution (Folge-Schritt)¶

    Aktuell werden die Templates manuell substituiert. Mit dem geplanten Packaging (Homebrew-Tap / DEB-Paket) werden Binary und Service-Unit zusammen ausgeliefert und beim Install vorbereitet — Konfiguration bleibt weiterhin Sache des Operators.
