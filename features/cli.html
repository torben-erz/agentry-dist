    CLI-Subcommands¶

    Der agentry-Daemon ist gleichzeitig sein eigener Verwaltungs-CLI. Ohne Argument startet er den Daemon (backwards-kompatibel mit existierenden Service-Definitionen); mit Subcommand übernimmt er Setup- und Operator- Aufgaben.

    Übersicht¶

    agentry [<subcommand>] [<argumente>]
    Subcommand Zweck
    daemon Startet den Daemon (Default ohne Subcommand).
    init [--force] Legt eine Default-Config unter ~/.agentry/config.json an.
    config validate [<pfad>] Lädt und validiert die Config. Exit 0/1.
    config show [<pfad>] Druckt die Config-Datei.
    status [--url <url>] Fragt den Health-Endpoint ab, druckt /status.
    logs [-n N] [-f] Tail über die Log-Datei (delegiert an tail).
    webhook install Legt Webhooks via Provider-API an (gh/glab), idempotent.
    webhook list Listet existierende Hooks pro Watch-Ziel.
    webhook delete <id> Entfernt einen Hook per ID.
    labels install Legt Status-/Trigger-Labels pro Watch-Ziel an, idempotent.
    labels delete [--name <label>] [--target <desc>] [--dry-run] Entfernt die vom Daemon erwarteten Labels wieder.
    diagnose Markdown-Block mit Version, Plattform, Tools, Sandbox-Status, Config-Health, jüngste Log-Fehler — für Beta-Bug-Reports.
    update Single-Shot Update-Check gegen das konfigurierte Distribution-Repo.
    version Version + Plattform.
    help Hilfe-Text.

    agentry init¶

    Schreibt eine kommentierte Default-Config nach ~/.agentry/config.json. Existiert die Datei bereits, weigert sich init — mit --force (oder -f) wird sie überschrieben.

    agentry init

    Das Template enthält die wichtigsten Schlüssel in lesbarer Reihenfolge und einen Platzhalter "OWNER/REPO" für watch. Der erste Aufruf nach Installation reicht aus, um anschließend nur noch watch, ggf. tokenFile und webhookSecretFile anzupassen.

    Watch-Shortcut

    init schreibt watch als String ("watch": "OWNER/REPO"). Der Config-Decoder akzeptiert sowohl die String-Shortcut-Form als auch die ausführliche Object-Form ({"type": "repo", "value": "..."}). Beide sind äquivalent — für Multi-Repo / OwnerScope ist die Object-Form erforderlich.

    agentry config validate¶

    Lädt die Config und schickt sie durch den ConfigValidator. Exit-Code 0, wenn alle Felder strukturell stimmen; 1 bei Validator-Fehler.

    agentry config validate
# oder mit explizitem Pfad:
agentry config validate /etc/agentry/config.json

    Bei Erfolg gibt der Befehl eine Zusammenfassung aus:

    Konfiguration ist gültig (/Users/.../.agentry/config.json).
  Provider:    github
  Watch:       repo:torben-erz/Agentry
  Backend:     claude-code
  Sandbox:     none
  Worker:      1
  Health:      127.0.0.1:8765
  Webhook:     deaktiviert

    Sind agentBackends- oder agentModels-Allowlists gesetzt (Pro-Ticket- Routing via Label), zählt die Ausgabe alle Einträge auf und markiert den Default explizit. Ohne Allowlist wird die Zeile weggelassen bzw. nur der Default angezeigt.

      Backends:    claude-code (Default), codex
  Modelle:     claude-sonnet-4-6 (Default), claude-opus-4-7, gpt-5-codex

    Validator prüft nur Struktur — Token-Verfügbarkeit und CLI-Tools werden erst beim Daemon-Start geprüft. Für einen vollständigen Smoke-Test: agentry daemon kurz starten und das Startup-Log beobachten.

    agentry config show¶

    Druckt den Inhalt der Config-Datei roh nach stdout — sinnvoll als Eingabe für jq oder zum schnellen Sichten in einem laufenden System:

    agentry config show | jq '.maxConcurrency'

    agentry status¶

    HTTP-GET auf den /status-Endpoint des laufenden Daemons. Default-URL wird aus der Config gebaut (healthHost/healthPort). Wer einen Daemon auf einem anderen Host abfragt:

    agentry status --url http://operations.internal:8765/status

    Exit-Code 0 bei HTTP 200, 1 sonst. Der Antwort-Body (JSON) landet auf stdout — pipe-able für Monitoring-Skripte.

    Details zu den Feldern: Health-Endpoint.

    agentry logs¶

    Tail über die persistierte Log-Datei aus der Config (logFile). Standardmäßig die letzten 50 Zeilen; mit -n N mehr; mit -f folgt der Befehl der Datei weiter (delegiert an tail -F — versteht Rotation).

    agentry logs -n 200            # letzten 200 Zeilen
agentry logs -f                # live mitlesen, durch Rotation hindurch
agentry logs -n 1000 -f        # backfill + live

    Wenn logFile in der Config auf null steht, gibt der Befehl einen Hinweis aus — Stdout-only-Logs sind durch agentry logs nicht erreichbar.

    agentry webhook¶

    Webhook-Auto-Setup gegen die Provider-API. Spart das Klicken in der GitHub/ GitLab-UI; idempotent — vorhandene Hooks mit derselben URL werden nicht zweimal eingetragen.

    Voraussetzungen: gh/glab ist im PATH und eingeloggt (oder das Token kommt via Provider-Env-Var), und in der Daemon-Config steht ein auflösbares Webhook-Secret (AGENTRY_WEBHOOK_SECRET oder webhookSecretFile).

    agentry webhook install --url <URL>¶

    Legt einen Webhook pro Watch-Ziel an. Die URL ist die öffentliche Adresse, unter der dein WebhookServer erreichbar ist (typisch via Reverse-Proxy mit TLS).

    # GitHub Single- oder Multi-Repo
agentry webhook install --url https://agentry.example.com/webhook/github

# GitLab Single- / Multi-Project / Group-Scope
agentry webhook install --url https://agentry.example.com/webhook/gitlab

# Plan zeigen, ohne API zu rufen
agentry webhook install --url https://x.example.com/webhook/github --dry-run
    Provider Watch Aktion
    GitHub repo POST /repos/<repo>/hooks
    GitHub repos je Repo ein Hook
    GitHub ownerScope nicht unterstützt — Org-Hooks vs. User-Hooks haben unterschiedliche APIs. Bitte pro Repo installieren.
    GitLab repo POST /projects/<id>/hooks
    GitLab repos je Projekt ein Hook
    GitLab ownerScope ein Group-Hook via POST /groups/<id>/hooks — neue Projekte in der Gruppe sind damit automatisch abgedeckt.

    Events: GitHub abonniert issues + pull_request; GitLab abonniert issues_events + merge_requests_events. SSL-Verifizierung ist beide Mal an — passt, wenn der Reverse-Proxy ein gültiges Zertifikat liefert.

    agentry webhook list¶

    Listet existierende Hooks pro Watch-Ziel — zur Bestandsaufnahme oder zum Finden eines Hook-IDs für delete.

    agentry webhook list
# github-repo:acme/agentry:
#   id=12345  https://agentry.example.com/webhook/github
# github-repo:acme/other:
#   (keine Hooks)

    agentry webhook delete <id>¶

    Entfernt einen Hook per ID. Bei mehreren Watch-Zielen muss --target mit der Description (github-repo:... / gitlab-project:... / gitlab-group:...) das Ziel präzisieren:

    agentry webhook delete 12345
agentry webhook delete 67890 --target gitlab-project:group/sub/project

    agentry labels install¶

    Legt die Status- und Trigger-Labels pro Watch-Ziel an. Idempotent — bei GitHub via gh label create --force (existierende Labels werden mit den neuen Werten aktualisiert), bei GitLab über tolerantes Ignorieren von „already exists"-Fehlern.

    agentry labels install

    Die Label-Liste kommt aus der Config: triggerLabel/reviseLabel werden eingesetzt (wenn umbenannt), plus die fixen Status-Labels (agent:in-progress, agent:done, agent:failed, agent:revising, agent:revised, agent:revise-failed). Wenn agentBackends/agentModels aktiv sind, kommen zusätzlich die passenden Routing-Labels (agent:backend:<id>, agent:model:<wert>) — sonst gibt's keine toten Labels in der UI.

    Provider Watch Aktion
    GitHub repo / repos pro Repo gh label create --force
    GitHub ownerScope nicht unterstützt — GitHub kennt keine Org-Issue-Labels.
    GitLab repo / repos pro Projekt glab label create
    GitLab ownerScope nicht unterstützt — Group-Labels gelten für Issues/MRs nicht direkt; bitte pro Projekt installieren.

    agentry labels delete¶

    Gegenstück zu labels install — entfernt die vom Daemon erwarteten Labels wieder aus jedem Watch-Ziel. Idempotent: ein nicht existierendes Label gibt notFound zurück statt zu failen, damit ein Re-Run nach Teil-Erfolg sauber durchläuft.

    agentry labels delete                                # alle Daemon-Labels aus allen Watch-Zielen
agentry labels delete --dry-run                      # Plan-Vorschau ohne API-Aufruf
agentry labels delete --name agent:done              # nur ein einzelnes Label
agentry labels delete --target github-repo:foo/bar   # auf ein Ziel einschränken

    Destruktiv: gh label delete / glab label delete entfernen das Label gleichzeitig von allen Issues/PRs, die es tragen — Status-Tracking ist danach weg. Vor dem Aufruf bewusst entscheiden, ob die Watch-Ziele nicht mehr vom Daemon bedient werden.

    --name ist auf die vom Daemon erwarteten Labels (Default + aktive Routing-Labels) beschränkt; ein freier Name wird mit Liste der gültigen Werte abgelehnt. Wer beliebige Repo-Labels löschen will, ruft direkt gh label delete bzw. glab label delete.

    --target akzeptiert die gleiche stabile CLI-Form wie webhook delete (github-repo:owner/name, gitlab-project:group/sub/project); bei mehreren Watch-Zielen ohne --target werden alle bedient.

    agentry diagnose¶

    Sammelt einen kopierbaren Markdown-Block mit allem, was für ein Beta-Bug-Report nötig ist — und nichts darüber hinaus.

    agentry diagnose | pbcopy    # macOS: direkt in die Zwischenablage
agentry diagnose             # ausgeben und manuell kopieren

    Sektionen:

    • Agentry-Diagnose — Version, Erfassungszeit, Install-ID (anonymer Korrelations-Schlüssel aus ~/.agentry/install.id, kein Geheimnis).
    • System — Plattform-Identifier (macOS/Linux) + uname -a.
    • Externe Tools — Tabelle für git, swift, gh, glab, claude, codex und das plattform-passende Sandbox-Tool (sandbox-exec auf macOS, bwrap auf Linux). Pro Tool: gefunden via command -v plus erste Zeile aus --version.
    • Sandbox — Plattform-Default aus SandboxConfig.platformDefaultIdentifier.
    • Config — Pfad, Existenz, Validator-Status und die Schlüssel- Settings (Provider, Watch, Backend, Modell, Worker, Poll-Intervall, Sandbox-Default, Health-/Webhook-Server-Bindings). Die Token-Quelle wird beschrieben, nicht der Wert — tokenFile-Pfade werden ausgeblendet.
    • Jüngste Fehler aus dem Log — letzte 30 Zeilen mit Level [WARN] oder [ERROR] aus config.logFile. INFO-Zeilen kommen bewusst nicht rein.

    Was der Block bewusst nicht enthält: Tokens, Webhook-Secrets, Inhalt der Tickets oder Commits, vollständige tokenFile-Pfade. Der Block ist so designed, dass er sicher per E-Mail oder Chat geteilt werden kann.

    Run-Time: 2–5 Sekunden (limitiert durch die einzelnen Tool---version- Aufrufe).

    agentry update¶

    Single-Shot Update-Check gegen das konfigurierte Distribution-Repo. Nutzt den gleichen Notifier-Pfad wie der Daemon, druckt das Ergebnis aber auf stdout statt ins Log — gedacht für Skripte, CI-Checks oder schnelles Nachschauen zwischen Daemon-Restarts.

    agentry update

    Exit-Codes:

    Code Bedeutung
    0 Aktuelle Version oder Update verfügbar — beides informativ.
    2 Netz-/Parse-Fehler, Repo nicht erreichbar, kein Release verfügbar.

    0 bei beiden Erfolgs-Fällen ist Absicht: das Kommando ist informativ, nicht „ist Update nötig?". Wer den Update-Zustand maschinell auswerten will, parst stdout.

    Details zum Verhalten + Prerelease-Awareness + Homebrew-Erkennung + Konfigurations-Schlüssel in Update-Notifier.

    agentry version / agentry help¶

    Version (inkl. Plattform) bzw. Hilfetext. Werden zusätzlich auf die kurzen Flags -v/--version und -h/--help gemappt.

    Backwards-Compat¶

    Ohne Argument verhält sich agentry wie der bisherige Daemon (agentry = agentry daemon). Existierende launchd-Plists und systemd-Units, die nur das Binary ohne Argumente starten, brauchen nichts umstellen.
