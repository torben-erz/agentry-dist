    Token-Handling¶

    Agentry braucht ein Provider-Token (GitHub-PAT, GitLab-PAT, …) für API-Calls, Issue-Kommentare, PR/MR-Erstellung und git-Push. Das Token kommt aus einer von fünf Quellen — in dieser Default-Priorität:

    flowchart LR
    A[Daemon-Start] --> B{"1. Env-Variable<br/>AGENTRY_*_TOKEN?"}
    B -->|gesetzt| OK[Token]
    B -->|leer| C{"2. Keychain<br/>(macOS)<br/>konfiguriert?"}
    C -->|gesetzt + Item da| OK
    C -->|nicht da| D{"3. libsecret<br/>(Linux)<br/>konfiguriert?"}
    D -->|secret-tool liefert| OK
    D -->|nicht da| E{"4. tokenFile<br/>in Config?"}
    E -->|gesetzt + 0600| OK
    E -->|nicht da| F["5. gh/glab<br/>auth token"]
    F --> OK
    OK --> Z["GH_TOKEN /<br/>GITLAB_TOKEN<br/>exportieren"]
    Z --> Y[Daemon läuft]

    Config.tokenSource (optional) erzwingt eine einzelne Quelle, statt die Reihenfolge abzuklappern — sinnvoll, wenn Compliance „nur Keychain" verlangt oder vorhandene Env-Variablen ignoriert werden sollen.

    Quelle 1 — Environment-Variable¶

    export AGENTRY_GITHUB_TOKEN='ghp_…'   # bzw. AGENTRY_GITLAB_TOKEN
agentry

    Praktisch für Container, CI, systemd-Units. Das Token kommt aus dem Orchestrator (Docker-Secret, systemd-EnvironmentFile=, …) und wird nie auf Disk geschrieben.

    Quelle 2 — macOS-Keychain¶

    Setup einmalig:

    security add-generic-password \
  -s com.nanoapes.agentry \
  -a github \
  -w ghp_xxxxxxxxxxxxxxxx \
  -U   # update wenn schon vorhanden

    Config:

    {
  "provider": "github",
  "tokenKeychainService": "com.nanoapes.agentry"
}

    Account-Name ist automatisch github oder gitlab (provider-abhängig). Der Daemon liest beim Start via Security.framework (kein Subprozess) — Plattform-Guard #if os(macOS): auf Linux ist die Quelle inaktiv.

    Headless-Hinweis: Beim ersten Lese-Versuch fragt macOS einmal nach Zugriff. Bei launchd-Daemons ohne UI-Session: das Keychain-Item beim Anlegen mit -A (allow any application) freigeben oder ein separates Login-Keychain für den Service-User pflegen.

    Quelle 3 — Linux-libsecret¶

    Setup einmalig (Paket: libsecret-tools auf Ubuntu/Debian):

    sudo apt install libsecret-tools
echo -n 'ghp_xxxxxxxxxxxxxxxx' | secret-tool store \
  --label "Agentry GitHub Token" \
  service agentry \
  account github

    Config (Default-Attribute matchen die Setup-Konvention):

    {
  "provider": "github"
}

    Oder explizit andere Attribute:

    {
  "tokenLibsecretAttributes": {
    "service": "my-vault",
    "account": "agentry-prod"
  }
}

    Der Daemon ruft secret-tool lookup <attr> <val> …. Ist secret-tool nicht installiert, wird die Quelle leise übersprungen — die Hierarchie fällt weiter zur Token-Datei oder zum CLI-Fallback.

    Quelle 4 — Token-Datei¶

    { "tokenFile": "/etc/agentry/github.token" }

    Der gesamte Datei-Inhalt (nach Trimming) wird als Token verwendet. Permissions müssen 0600 oder strikter (z. B. 0400) sein:

    sudo install -m 600 -o agentry -g agentry /dev/null /etc/agentry/github.token
sudo bash -c 'echo "ghp_..." > /etc/agentry/github.token'
sudo chmod 600 /etc/agentry/github.token

    Bei lockereren Permissions verweigert Agentry den Start mit klarer Fehlermeldung:

    Token-Datei /etc/agentry/github.token hat Permissions 644 — zu locker.
Erforderlich: 0600 (`chmod 600 /etc/agentry/github.token`).

    Quelle 5 — gh / glab auth token (Fallback)¶

    Wenn keine der vier vorherigen Quellen ein Token liefert, ruft Agentry gh auth token (bei provider: github) bzw. glab auth token (bei provider: gitlab). Voraussetzung: gh auth login bzw. glab auth login wurde einmalig ausgeführt. Ideal für lokale Dev-Setups.

    Quelle erzwingen via tokenSource¶

    { "tokenSource": "keychain" }

    Erlaubte Werte: "env", "keychain", "libsecret", "file", "cli". Wenn die erzwungene Quelle nicht liefert, wirft der Daemon — es gibt kein stilles Fallback. Sinnvoll für Compliance-Setups, wo nur ein einzige Token-Pfad zugelassen sein darf.

    tokenSource: null (Default) → Default-Reihenfolge wie oben.

    Token-Rotation via SIGHUP¶

    Tokens haben oft kürzere Lebensdauer als Daemon-Uptime (GitHub-App-Tokens: 1 h, kurzlebige PATs: 7 Tage). Statt den Daemon neuzustarten:

    # 1. Neues Token in der Quelle ablegen
security add-generic-password -s com.nanoapes.agentry -a github -w ghp_NEW -U
# oder: echo 'ghp_NEW' > /etc/agentry/github.token
# oder: AGENTRY_GITHUB_TOKEN nicht änderbar im laufenden Prozess
#       → Keychain/libsecret/Datei sind die praktischen Pfade

# 2. SIGHUP an den Daemon
kill -HUP $(pgrep -f 'agentry daemon')

    Der TokenRotator (eigene Datei Sources/agentry/TokenRotator.swift) löst dann einen Re-Resolve aus, der die konfigurierte Quellen-Hierarchie neu abklappert und das frische Token in GH_TOKEN/GITLAB_TOKEN setzt. Polling-/Worker-Loops nutzen das neue Token ab dem nächsten Subprozess- Aufruf.

    Logging:

    TokenRotator: Token neu geladen aus macOS-Keychain (service='com.nanoapes.agentry', account='github'). GH_TOKEN im Prozess-Env aktualisiert.

    Bei einem Refresh-Fehler bleibt der alte Token im Env aktiv und der Daemon loggt:

    TokenRotator: Refresh fehlgeschlagen — <reason>. Alter Token bleibt im Env.

    Hinweis Env-Variable: Wer in der Default-Reihenfolge bleibt und das Env-Token rotieren will, hat ein Problem — ein laufender Prozess sieht den Env-Wert beim Start, nicht beim Refresh. Lösung: für rotierende Tokens Keychain/libsecret/Datei nutzen.

    Was passiert mit dem Token nach dem Resolve?¶

    1. In den GitHubClient / GitLabClient für REST-API-Aufrufe.
    2. In die Process-Env als GH_TOKEN / GITLAB_TOKEN — damit alle gh/glab-Subprocesses und git-Credential-Helpers dieselbe Auth nutzen. Kein interaktiver Login mehr nötig in Headless-Setups.
    3. Nicht in Logs — die Logzeile zeigt nur die Quelle:
    Token bezogen aus: macOS-Keychain (service='com.nanoapes.agentry', account='github').

    Welche Token-Scopes brauche ich?¶

    GitHub¶

    Scope Wofür
    repo Issues lesen, Kommentare schreiben, Branches pushen, PRs erstellen
    workflow nur nötig wenn der Agent Workflow-Files ändern darf
    read:org nur bei watch.ownerScope mit Org-Zugriff

    GitLab¶

    Scope Wofür
    api Vollzugriff für Polling, Webhook-Setup, Issue/MR-Updates
    read_repository / write_repository git-Push via Token-URL

    Sicherheits-Eigenschaften¶

    Quelle Auf Disk? Sichtbar via …
    Env-Variable nein ps -E, /proc/<pid>/environ (root oder Owner)
    macOS-Keychain ja, verschlüsselt Keychain-Access-UI, security-CLI mit Berechtigung
    Linux-libsecret ja, vom Session-Keyring verwaltet Seahorse-UI / secret-tool
    Token-Datei ja, mit 0600 nur Owner kann lesen
    gh auth token ja, in ~/.config/gh/hosts.yml gh-CLI managed

    Im Daemon liegt das Token im RAM und in der Process-Env. Wer /proc/<pid>/environ lesen kann (root, Owner), sieht es. Bei strikten Anforderungen muss eine Sandbox-/User-Trennung dazukommen — siehe Sandbox.
