    PR-Review-Loop¶

    Der Daemon kann nicht nur frische Issues verarbeiten, sondern auch auf Reviewer- Feedback an einem bestehenden Pull Request reagieren. Reviewer setzt das Label agent-revise, der Agent iteriert auf demselben Branch weiter und pusht neue Commits. Aus „Einweg: Issue → PR" wird „Schleife: Reviewer ↔ Agent".

    Ablauf aus Reviewer-Sicht¶

    1. Der Agent hat einen PR aus einem Issue erstellt — typischer Fresh-Workflow.
    2. Im PR-Review hinterlässt der Reviewer Kommentare (inline oder als Review-Body).
    3. Reviewer setzt das Label agent-revise auf den PR.
    4. Der Daemon greift den PR im nächsten Polling-Tick auf, setzt agent:revising, checkt den PR-Branch in einen Worktree aus und ruft den Agenten auf.
    5. Der Agent liest seine bisherigen Commits sowie das Reviewer-Feedback (über gh pr view und gh api .../comments) und macht die nötigen Änderungen.
    6. Pipeline committet, pusht auf denselben Branch, kommentiert am PR und flippt die Labels: agent-revise raus, agent:revising raus, agent:revised rein.
    7. Reviewer prüft erneut. Falls weiter Anpassungen nötig: agent-revise einfach wieder setzen — der Daemon iteriert.

    Konfiguration¶

    {
  "reviseEnabled": true,
  "reviseLabel": "agent-revise"
}
    Schlüssel Default Bedeutung
    reviseEnabled true Wenn false, ignoriert der Daemon Revise-Tickets vollständig — kein zusätzliches Polling, keine Bearbeitung.
    reviseLabel "agent-revise" Label-Name, mit dem Reviewer den Agent triggern. Muss sich von triggerLabel unterscheiden.

    Validator weist beide Defaults durch und blockt explizit, wenn triggerLabel == reviseLabel.

    Status-Labels¶

    Label Bedeutung
    agent-revise Trigger-Label. Reviewer setzt es; Daemon entfernt es nach Abschluss.
    agent:revising Lock-Label während eines Revise-Laufs. Wie agent:in-progress, aber für PRs.
    agent:revised Letzter Revise-Lauf erfolgreich abgeschlossen.
    agent:revise-failed Letzter Revise-Lauf gescheitert (Phase im PR-Kommentar).

    Polling¶

    Wenn reviseEnabled = true, fragt der Daemon pro Tick zwei Endpoints ab:

    • …?labels=<triggerLabel> für frische Issues.
    • …?labels=<reviseLabel> für Revise-PRs.

    Beide nutzen separate ETag-Dateien, sodass 304-Antworten weiterhin keine Rate-Limit-Quota verbrauchen. Pro entdecktem Revise-PR macht der Daemon einen zusätzlichen API-Call (GET /repos/<repo>/pulls/<n>), um Head- und Base-Branch zu ermitteln. Bei typischer Last (ein paar offene Revise-PRs) bleibt das weit unter dem Stunden-Quota.

    TicketQueue: keine Persistenz für Revise¶

    Im Gegensatz zur Fresh-Pipeline schreibt der Daemon Revise-Tickets nicht in die persistente processed-Liste — sonst wäre eine zweite Iteration desselben PRs blockiert. Die Lifecycle ist:

    1. Polling findet PR mit agent-revise.
    2. TicketQueue.claim → inFlight (Schutz gegen doppelten Pickup im selben Tick).
    3. Pipeline läuft.
    4. TicketQueue.markCompletedTransient → entfernt aus inFlight, schreibt nichts in processed.

    Dass Reviewer den PR mehrfach revisen können, ist also explizit gewollt — das Trigger-Label agent-revise übernimmt die Rolle des De-Triggers (Daemon entfernt es; nächster Pickup nur, wenn Reviewer es erneut setzt).

    Branch-Handling im Workspace¶

    Fresh-Pipeline: git worktree add … -b agent/ticket-N origin/main — neuer Branch.

    Revise-Pipeline: git worktree add -B <head> … origin/<head> — bestehender PR-Branch wird forciert auf den Origin-Tip gesetzt. Damit ist der Worktree garantiert auf dem letzten gepushten Stand des PRs, egal was im Bare-Cache aus früheren Läufen noch steht.

    Crash-Recovery¶

    Wenn der Daemon mitten in einem Revise-Lauf abstürzt, bleibt agent:revising am PR hängen. Beim nächsten Start räumt CrashRecovery das auf — analog zu agent:in-progress: Label wird auf agent:revise-failed geflippt, Trigger-Label entfernt, Kommentar mit Hinweis am PR, dass Reviewer erneut triggern darf.
