    Troubleshooting¶

    Konkrete Probleme + Lösungen, sortiert nach Lebenszyklus-Phase. Wenn du nicht weiterkommst: Bug-Report-Pfad ganz unten.

    Erstes Vorgehen — vor jedem Bug-Report drei Schritte¶

    Bei jedem Problem zuerst diese drei Befehle:

    agentry config validate          # 1. Config-Fehler?
agentry diagnose                 # 2. Toolchain, Plattform, Sandbox, letzte Logs
agentry logs -n 100              # 3. Was hat der Daemon zuletzt gemacht?

    Viele „Daemon tut nichts"-Berichte lösen sich beim Config-Check oder beim Lesen der letzten Log-Zeilen. agentry diagnose ist der Output, den du in jeden Bug-Report einkippst — er enthält genau die Infos, die zur Diagnose nötig sind, und keine Tokens/Secrets/Code.

    Installation & Setup¶

    brew tap torben-erz/agentry schlägt fehl¶

    Symptom:

    Error: Tap not found

    Wahrscheinliche Ursache: Du bist nicht auf macOS oder Linuxbrew — auf Windows funktioniert das nicht.

    Diagnose:

    brew --version
uname -s

    Lösung: macOS 14+ oder Linux mit Linuxbrew nutzen. Windows-Support ist nicht geplant; siehe FAQ → Welche Plattformen.

    brew install agentry schlägt fehl mit „SHA256 mismatch"¶

    Symptom:

    Error: SHA256 mismatch
Expected: a3b...
Actual:   f1c...

    Wahrscheinliche Ursache: Der Tap-Cache von Homebrew ist veraltet — es gibt ein neueres Release, dessen Hash nicht im lokalen Tap-Stand liegt.

    Lösung:

    brew untap torben-erz/agentry
brew tap torben-erz/agentry
brew install agentry

    agentry: command not found nach Installation¶

    Symptom: brew install lief durch, aber agentry ist nicht im PATH.

    Diagnose:

    brew list agentry           # zeigt installierte Dateien
which agentry || echo "nicht im PATH"

    Lösung: Das Symlink-Verzeichnis von Homebrew muss im $PATH sein — auf Apple Silicon /opt/homebrew/bin, auf Intel /usr/local/bin, auf Linuxbrew /home/linuxbrew/.linuxbrew/bin. Wenn das Shell-Profil das nicht setzt:

    # Apple Silicon
eval "$(/opt/homebrew/bin/brew shellenv)"

# Intel
eval "$(/usr/local/bin/brew shellenv)"

    Dauerhaft in ~/.zshrc / ~/.bashrc eintragen.

    macOS: „cannot be opened because it is from an unidentified developer"¶

    Symptom: Beim ersten Start kommt ein Gatekeeper-Dialog.

    Wahrscheinliche Ursache: Du hast das Binary außerhalb von Homebrew manuell heruntergeladen, und das Quarantäne-xattr ist gesetzt.

    Diagnose:

    xattr -p com.apple.quarantine $(which agentry) 2>/dev/null && echo "quarantined"
codesign --verify --verbose=2 $(which agentry)

    Lösung: Wenn codesign --verify durchläuft (Binary ist signiert und notarisiert), reicht es, das Quarantäne-Attribut zu entfernen:

    xattr -d com.apple.quarantine $(which agentry)

    Bei via Homebrew installierten Binaries tritt das nicht auf — Brew extrahiert ohne Quarantäne.

    agentry init weigert sich¶

    Symptom:

    Konfiguration existiert bereits unter ~/.agentry/config.json.
Mit --force überschreiben.

    Wahrscheinliche Ursache: Die Datei existiert schon (z. B. aus vorigem Setup).

    Lösung: Datei prüfen, ob sie noch gebraucht wird:

    agentry config show

    Wenn sie veraltet ist und du sicher mit dem Default-Stand neu starten willst:

    mv ~/.agentry/config.json ~/.agentry/config.json.bak
agentry init

    --force überschreibt direkt, aber dabei gehen watch, tokenFile und alle bewusst gesetzten Schalter verloren — lieber erst sichern.

    agentry config validate schlägt fehl¶

    Symptom:

    Config-Fehler: 'watch' ist Pflicht — siehe docs/referenz/config.md.
Exit 1.

    Lösung: Der Validator-Output nennt den genauen Schlüssel. Die volle Validator-Regel-Tabelle steht in Referenz → Config. Die häufigsten Fehler:

    • watch fehlt oder ist leer — Pflichtschlüssel, siehe Konfiguration → Stufe 1
    • agentBackend ist ein unbekannter Name — gültig sind "claude" und "codex"
    • sandbox.default-Strategie kennt der Daemon nicht — gültig sind "none", "macos-sandbox", "linux-bwrap"
    • tokenFile zeigt auf eine Datei, die nicht existiert oder nicht 0600 ist

    Daemon-Start¶

    Daemon stoppt beim Start mit „Default-Sandbox nicht verfügbar"¶

    Symptom (Linux):

    ERROR: Default-Sandbox 'linux-bwrap' ist auf diesem Host nicht verfügbar
— Daemon stoppt aus Sicherheits-Gründen, statt stillschweigend ohne
Sandbox zu laufen. Hinweis: 'bwrap' muss installiert sein
(`sudo apt install bubblewrap`).

    Wahrscheinliche Ursache: bubblewrap ist nicht im System-PATH.

    Lösung:

    sudo apt install bubblewrap                   # Debian/Ubuntu
sudo dnf install bubblewrap                   # Fedora
which bwrap                                   # verifizieren

    Alternativ (nicht empfohlen, aber möglich für lokale Tests):

    { "sandbox": { "default": "none" } }

    Damit läuft Agentry ohne Filesystem-Isolation. Nicht für produktive Setups.

    Daemon stoppt mit „Kein Token gefunden"¶

    Symptom:

    ERROR: Kein GitHub-Token aus einer der Quellen verfügbar (Env, Keychain,
libsecret, Datei, gh CLI).

    Diagnose:

    echo $AGENTRY_GITHUB_TOKEN                    # 1. Env-Variable?
gh auth status                                # 2. gh-CLI eingeloggt?
ls -la ~/.agentry/                            # 3. tokenFile-Pfad richtig?

    Lösung: Mindestens eine der fünf Quellen muss liefern. Einfachster Pfad: gh auth login — dann fällt Agentry auf den CLI-Token zurück. Details zur Token-Hierarchie: Token-Handling.

    Port 8765 bereits in Benutzung¶

    Symptom: Daemon-Start bricht ab oder Health-Endpoint antwortet nicht.

    Diagnose (macOS/Linux):

    lsof -i :8765 -nP

    Lösung: Anderen Port in der Config setzen:

    { "healthPort": 8775 }

    Oder den belegenden Prozess beenden, falls das ein älterer Daemon- Instance ist.

    Daemon startet, aber „Polling: keine Tickets" obwohl Issues mit Label agent-task existieren¶

    Symptom: Daemon läuft, im Log steht alle paar Sekunden:

    [INFO] Polling owner/repo: 0 Tickets mit Label 'agent-task' gefunden, 0 bereit.

    …aber im Repo siehst du ein Issue mit dem Label.

    Wahrscheinliche Ursachen + Lösungen:

    1. Falsches watch-Repo — agentry config show | grep watch und gegen GitHub-URL vergleichen. Großschreibung beachten!
    2. Token hat keinen Lesezugriff auf das Repo — privates Repo + PAT ohne repo-Scope. Test: 
      gh api /repos/<owner>/<repo>/issues?labels=agent-task
      Wenn das 403 gibt: Token-Scope reicht nicht.
    3. Issue hat bereits Status-Labels — Issues mit agent:in-progress, agent:done, agent:failed werden vom Polling herausgefiltert. Status-Label entfernen oder agent:failed durch erneutes Setzen von agent-task zurücksetzen.
    4. Issue ist eigentlich ein PR — GitHub mischt Issues und PRs am gleichen Endpoint. Agentry filtert PRs aus dem Fresh-Polling raus; wenn du auf einem PR agent-task setzt, passiert nichts. Für PRs gibt es agent-revise.

    Ticket-Verarbeitung¶

    Ticket bleibt auf agent:in-progress hängen¶

    Symptom: Ein Issue hat seit längerer Zeit das Label agent:in- progress, aber kein PR wurde erzeugt und keine weitere Log-Aktivität.

    Diagnose:

    agentry status                                  # Worker-Aktivität
agentry logs -n 200 | grep -i "ticket #<n>"     # Letzte Log-Zeilen zu diesem Ticket

    Lösung:

    • Wenn der Worker noch arbeitet (Status sagt „active worker 1"): warten. Agent-Lauf kann bis agentTimeoutSeconds (Default 30 min) dauern.
    • Wenn der Worker idle ist: Daemon ist seit dem Ticket-Start gecrasht und neu gestartet. CrashRecovery hat das Ticket ggf. schon auf agent:failed gesetzt — sonst manuell: 
      gh issue edit <n> -R <owner>/<repo> \
    --remove-label "agent:in-progress" \
    --add-label "agent-task"

    Mehr Detail: Features → Crash-Recovery.

    Ticket failt mit PipelineFailure(phase: .agentRun)¶

    Symptom: Issue bekommt agent:failed-Label, im PR-Kommentar steht:

    Pipeline-Abbruch in Phase 'agentRun': Agent-Backend 'claude'
endete mit Exit 1.

    Diagnose: Agentry loggt seit Phase 4.42 bei Non-Zero-Exit automatisch eine WARN-Zeile mit stdout- und stderr-Preview (je 1000 Zeichen, (leer)-Marker wenn ein Stream nichts liefert). Das ist die erste Anlaufstelle:

    agentry logs -n 200 | grep -E "claude endete mit Exit|codex endete mit Exit"

    Bei der offiziellen claude-CLI landen Auth-/Quota-Hinweise oft auf stdout statt stderr — deshalb deckt der warn-Log beide Streams ab.

    Wahrscheinliche Ursachen:

    1. Claude/Codex-CLI nicht eingeloggt — claude --version muss eine Version ausgeben UND ein API-Token konfiguriert haben. Wenn der Daemon als Service-User läuft (launchd/systemd): der CLI-Auth- Zustand ist pro Unix-User — ein claude login als Operator-Account reicht nicht. Direkt als Service-User einloggen und dort claude login ausführen:
    # Wenn du sudo-Recht hast:
sudo -u agentry -i
# Oder direkt als Service-User per SSH/Konsole einloggen,
# falls der User keinen sudo-Eintrag hat.
# Dann:
claude login

    Headless-Alternative ohne interaktiven Browser-Login: API-Key über ANTHROPIC_API_KEY im Service-Manifest (Plist/Systemd-Unit) setzen.

    Vor dem nächsten Ticket testen: agentry auth check macht einen Single-Shot über alle konfigurierten Backends (kein Daemon nötig). Bei OAuth-Setups, die stundenlang idle stehen, lohnt sich zusätzlich authWatchdogEnabled: true in der Config — der Watchdog meldet Token-Verfall, bevor das nächste Ticket darauf läuft. Details: Features → Auth-Watchdog. 2. Modell nicht erreichbar — Anthropic/OpenAI-Service-Status prüfen 3. Permission-Modus blockiert — passiert nicht mehr mit --permission-mode bypassPermissions, den Agentry default setzt; wenn doch: claude --version neu prüfen, Update kann eine Inkompatibilität gebracht haben 4. Sandbox blockt einen Pfad, den der Agent braucht — Symptom: Sandbox-Violation im stderr-Preview der warn-Zeile. Lösung: extraReadOnlyBinds / extraWritePaths in sandbox.strategies ergänzen.

    Ticket failt in Phase .push¶

    Symptom:

    Pipeline-Abbruch in Phase 'push': git push schlug fehl mit Exit-Code 128.

    Wahrscheinliche Ursachen:

    1. Branch ist geschützt — wenn der Default-Branch in den Repo- Settings „nur PRs" erlaubt, schlägt direkter Push fehl. Agentry pusht auf agent/ticket-<n>, nicht auf main — also normalerweise kein Problem. Aber: wenn deine Regel auch Branches mit Prefix agent/ schützt, geht's schief
    2. Token hat keinen Schreibzugriff — Test: gh auth status sollte repo (write) zeigen
    3. gh auth setup-git-Credential-Helper nicht aktiv — wird vom Daemon beim Start registriert, aber bei manuellen Setups manchmal übergangen. Re-registrieren: gh auth setup-git

    PR wird angelegt, aber Issue bekommt kein agent:done-Label¶

    Symptom: Branch + PR sind da, aber das Issue zeigt noch agent:in-progress.

    Wahrscheinliche Ursache: Der Daemon ist nach dem PR-Push gecrasht, bevor er das Status-Label flippen konnte.

    Lösung: Manuell:

    gh issue edit <n> -R <owner>/<repo> \
    --remove-label "agent:in-progress" \
    --add-label "agent:done"

    CrashRecovery erkennt das beim nächsten Start als „bereits erledigt" und überspringt es.

    Revise-Loop reagiert nicht auf agent-revise-Label¶

    Symptom: Du setzt agent-revise auf einen offenen PR, im Daemon- Log passiert nichts.

    Diagnose:

    agentry config show | grep -i revise          # reviseEnabled: true?
gh pr view <n> -R <owner>/<repo> --json labels

    Lösung:

    1. reviseEnabled: false in der Config — auf true setzen
    2. Falsches reviseLabel — Default ist "agent-revise". Wenn du den Namen geändert hast, muss das Label im Repo angepasst werden: 
      agentry labels install
    3. PR ist geschlossen oder gemergt — Revise greift nur auf offene PRs

    Update & Distribution¶

    agentry update sagt „Update-Check fehlgeschlagen"¶

    Symptom:

    Update-Check fehlgeschlagen: GitHub-Release konnte nicht abgefragt werden.
Exit 2.

    Wahrscheinliche Ursachen:

    1. Kein Internet — verifizieren mit curl -I https://api.github.com
    2. Rate-Limit — anonymer Public-API-Limit ist 60/h. Bei aggressivem Restart-Verhalten erreicht
    3. updateCheckRepo zeigt ins Leere — Default ist torben-erz/agentry-dist. Bei eigenen Forks/Mirrors muss das Repo öffentlich sein
    4. Distribution-Repo hat noch keine Releases — kann bei sehr frischer Installation passieren

    brew upgrade agentry macht nichts trotz Update-Hinweis¶

    Symptom: Daemon-Log sagt „Update verfügbar: vX.Y.Z", aber brew upgrade zeigt „already up-to-date".

    Wahrscheinliche Ursache: Der lokale Tap-Cache ist nicht synchronisiert.

    Lösung:

    brew update                          # Tap-Stand neu holen
brew upgrade agentry

    Wenn brew update selbst hängt: Tap-Repo direkt frisch holen:

    brew untap torben-erz/agentry
brew tap torben-erz/agentry
brew upgrade agentry

    Bekannte Limitierungen (kein Bug)¶

    Limitierung Workaround / Stand
    Multi-Repo via Glob/Wildcard Nicht unterstützt — explizit auflisten oder OwnerScope nutzen
    Cross-Repo-Refactor in einem Ticket Pro Repo ein Ticket; selbst koordinieren
    Windows-Support Nicht geplant
    GitHub-OwnerScope mit agentry labels install Nicht unterstützt (siehe Warnung im Befehl) — pro Repo installieren
    GitLab-Group-Scope für Labels Nicht unterstützt — pro Projekt installieren
    Auto-Update (Daemon zieht Binary selbst) Bewusst nicht — brew upgrade deckt es ab
    Echte Multi-Tenancy Daemon ist single-tenant per Design — siehe Migrations-Pfad

    Wenn nichts hilft¶

    1. agentry diagnose | pbcopy ausführen — strukturierter Markdown- Block mit Version, Plattform, Tool-Verfügbarkeit, Sandbox-Status und den letzten 30 WARN/ERROR-Log-Zeilen. Keine Tokens, Secrets oder Code-Inhalte enthalten.
    2. Reproduktions-Schritte notieren (3–5 Zeilen):
    3. Was wolltest du?
    4. Welche Schritte führen zum Problem?
    5. Was hast du erwartet?
    6. Was ist tatsächlich passiert?
    7. An Torben Erz schicken — Kanal je nachdem, wie du an die Beta gekommen bist (Mail, Slack, …).

    Beim nächsten Beta-Release sind die hier gesammelten Fixes wahrscheinlich schon im Daemon — brew upgrade agentry, dann nochmal probieren.
