    Konfiguration im Überblick¶

    Agentry liest seine Einstellungen aus einer einzigen Datei:

    ~/.agentry/config.json

    Diese Seite ordnet die Schlüssel nach Lernschritten statt alphabetisch: was musst du setzen, was kannst du setzen, was ist sicherheits-relevant. Für die vollständige Schlüssel-Tabelle inkl. Validator-Regeln siehe Referenz → Config.

    Config anlegen und ändern¶

    agentry init                       # legt config.json mit Defaults an
$EDITOR ~/.agentry/config.json     # editieren
agentry config validate            # prüfen — exit 0 = ok
agentry config show                # Datei nach stdout drucken

    Wenn agentry init schon eine Datei findet, weigert es sich. --force überschreibt — aber nur nutzen, wenn du sicher bist (Token-Pfade und Watch-Konfiguration gehen sonst verloren).

    Stufe 1 — Pflicht: was du setzen MUSST¶

    Damit Agentry überhaupt loslegen kann:

    Schlüssel Was rein Beispiel
    watch Repo, das beobachtet werden soll "watch": "dein-account/dein-repo"
    agentBackend Welches Agent-CLI Agentry aufrufen soll "agentBackend": "claude-code" (oder "codex")

    Mehr braucht es im einfachsten Fall nicht — der Rest hat sinnvolle Defaults.

    Watch-Form

    watch akzeptiert sowohl die kurze String-Form ("owner/repo") als auch die ausführliche Object-Form ({"type": "repo", "value": "..."}). Für Multi-Repo ("type": "repos") oder OwnerScope ("type": "ownerScope") brauchst du die Object-Form — siehe Multi-Repo.

    Stufe 2 — Häufige Anpassungen¶

    Schalter, die du oft anfasst:

    Tempo und Last¶

    Schlüssel Default Wofür
    pollInterval 5 Sekunden Wie oft Agentry GitHub fragt. Kleiner = schnellere Reaktion, mehr API-Calls. ETag/304 macht Polling günstig — 5 s passen für die meisten Setups.
    maxConcurrency 1 Wie viele Tickets parallel laufen dürfen. Bei seriellem Default ist die Reihenfolge deterministisch; bei > 1 muss dein Agent-Anbieter (Claude/Codex) das mitmachen.
    agentTimeoutSeconds 1800 (30 min) Maximalzeit pro Agent-Lauf. Reicht für typische Code-Aufgaben; bei langen Refactors hochsetzen.

    Provider und Tokens¶

    Schlüssel Default Wofür
    provider "github" GitHub oder GitLab. Bei GitLab siehe GitLab-Source.
    host null (= Provider-Default) Hostname der Provider-Instanz. Für GitHub Enterprise Server den GHES-Hostnamen setzen (z. B. "github.example.com" → API unter …/api/v3). Für selbst-gehostetes GitLab analog (z. B. "gitlab.example.com"). Default-Hosts: github.com / gitlab.com.
    tokenFile null Pfad zu einer 0600-Datei mit dem Token. Default-Fallback: gh auth token / glab auth token.
    tokenSource null Erzwingt eine einzelne Quelle ("env", "keychain", "libsecret", "file", "cli"). Compliance-Schalter.

    Mehr zur Token-Hierarchie: Features → Token-Handling.

    Trigger-Pfad¶

    Schlüssel Default Wofür
    triggerLabel "agent-task" Welches Label Agentry als „bitte bearbeiten" interpretiert.
    reviseLabel "agent-revise" Label für inkrementelle PR-Revisionen.
    reviseEnabled true Revise-Loop an/aus.
    webhookEnabled false Wenn true, lauscht Agentry zusätzlich auf POST /webhook/github (oder /webhook/gitlab) für instant-Trigger statt nur Polling.

    Agent-Banner (Optisches in Kommentaren + Commits)¶

    Schlüssel Default Wofür
    agentBanner true Ob Agentry eine Banner-Zeile (🟧 Claude Code · claude-opus-4-7 o. ä.) als Prefix in PR-/Issue-Kommentare und in den PR-Body schiebt und einen Co-Authored-By:-Trailer in jeden Agent-Commit setzt. Auf false setzen, wenn du die Kommentare lieber „nackt" hast oder den Sekundär-Avatar im Commit-View nicht möchtest.

    Wirkung des Banners:

    • Kommentare (Fresh + Revise, Erfolg + Fehler): erste Zeile zeigt Agent-Backend und Modell — Reviewer wissen sofort, ob Claude oder Codex den Kommentar produziert hat.
    • PR-Body: gleiche Banner-Zeile als Header über dem Closes #N.
    • Commit-Message: Banner als Body-Zeile + Co-Authored-By:-Trailer → GitHub/GitLab zeigt einen Sekundär-Avatar (grau, weil noreply@anthropic.com/noreply@openai.com zu keinem User-Account gehört) neben dem Primary-Author. Im git log und im Diff/Files-Tab des PRs sieht man so auf einen Blick, welcher Agent welchen Commit gemacht hat.

    Plattform-agnostisch — gleiche Wirkung bei GitHub, GitLab und kommenden Providern. Wenn du später echte Bot-Accounts (Pfad „eigener Token pro Backend") nutzen willst, ist das eine separate Option und unabhängig von agentBanner zu setzen.

    Branch-Basis¶

    Schlüssel Default Wofür
    baseBranch null (= pro Repo automatisch ermittelt) Branch, von dem die Fresh-Pipeline abzweigt und gegen den der erstellte PR geht (gh pr create --base <…>).

    Verhalten:

    • null → Agentry fragt pro Repo gh api repos/<repo> --jq .default_branch (bzw. glab api projects/<…> bei GitLab) und cached das Ergebnis. Für die meisten Setups die richtige Wahl, vor allem bei Multi-Repo mit unterschiedlichen Default-Branches (main hier, master dort).
    • "develop" (oder anderer String) → erzwingt diesen Branch global für alle überwachten Repos. Sinnvoll, wenn du einen Integrationszweig hast, von dem Agent-PRs ausgehen sollen statt vom Default-Branch.

    Revise gilt das nicht

    Der Revise-Loop ignoriert baseBranch — bei einer PR-Revision kommt die Base aus dem PR-Objekt selbst (head → base wie auf GitHub/GitLab sichtbar). baseBranch steuert nur die Fresh-Pipeline.

    Stufe 3 — Sicherheits-relevant¶

    Schalter, die du bewusst setzen solltest, bevor du Agentry in einem echten Repo laufen lässt:

    Sandbox¶

    Schlüssel Default Wofür
    sandbox.default plattform-abhängig (macOS: macos-sandbox, Linux: linux-bwrap) In welcher Isolation der Agent läuft. Plattform-Default ist bewusst gesandboxed — auf Linux ohne bubblewrap startet Agentry nicht.
    sandbox.strategies.<name> {} Strategie-spezifische Optionen (z. B. Custom-.sb-Profil für macOS, extra Bind-Mounts für linux-bwrap).
    sandbox.rules [] Routing-Regeln: pro Label oder Repo eine andere Sandbox.
    Was ist eine Sandbox? — Konzept-Erklärung (zum Aufklappen)

    Eine Sandbox ist eine isolierte Umgebung, in der ein Programm läuft, ohne dem Rest deines Systems schaden zu können. Das Betriebssystem (macOS-Kernel bzw. Linux-Kernel) blockiert Zugriffe, die der Agent nicht haben darf — z. B. das Schreiben außerhalb seines Workspace-Verzeichnisses.

    Warum braucht Agentry das?¶

    Der Agent (Claude Code, Codex, …) darf in seinem Workspace alles: Code ändern, Dateien anlegen, git-Befehle ausführen. Ohne Sandbox könnte ein versehentlicher oder bösartiger Befehl außerhalb des Workspaces:

    • deine ~/.ssh-Keys oder ~/.aws-Credentials lesen oder überschreiben
    • dein produktives Git-Repo direkt verändern
    • System-Konfigurationen unter /etc oder /usr modifizieren
    • Hintergrund-Prozesse starten, die nach dem Ticket weiterleben

    Mit Sandbox bleibt der Schreib-Zugriff auf den Workspace-Ordner und typische Build-Caches (~/.cache, ~/.npm, ~/.bun, …) begrenzt. Default ist out-of-the-box scharf — du musst nichts konfigurieren.

    Wie funktioniert das konkret?¶

    Strategie Plattform Mechanismus Durchsetzung
    macos-sandbox macOS sandbox-exec mit eingebettetem .sb-Profil macOS-Kernel
    linux-bwrap Linux bubblewrap mit Linux-Namespaces (Mount-Isolation, separate /tmp, eingeschränkte Bind-Mounts) Linux-Kernel
    none beide keine Isolation, Agent läuft frei —

    Beide Default-Strategien sind Kernel-Level: das Betriebssystem weist Schreib-Zugriffe ab, der Agent kann sie nicht umgehen.

    Wann braucht man none?¶

    • Debug-Lauf, wenn man die Sandbox als Verursacher eines Problems ausschließen will (kam in der Beta einmal vor — Pipe- und stdin-Bugs sahen am Anfang nach Sandbox-Problem aus).
    • Selbst-gehosteter CI-Runner, der schon in einem Container läuft und keine zweite Isolations-Schicht braucht.

    Per-Ticket-Override geht via Label agent:sandbox:none, ohne die globale Config anzufassen — siehe Features → Sandbox.

    Was die Sandbox NICHT ist¶

    • Keine VM-Isolation. Reads sind global erlaubt — der Agent sieht zwar ~/.ssh/id_rsa, kann aber nichts schreiben. Trotzdem: wenn der Agent den Schlüssel-Inhalt in einem Kommentar oder PR-Body leakt, hilft Sandbox nicht — das ist Token-Exfiltration auf Anwendungs-Ebene.
    • Kein Schutz gegen Prompt-Injection. Wenn ein bösartig formuliertes Issue den Agent zu unerwünschten Aktionen verleitet, laufen die innerhalb des erlaubten Workspaces. Die Sandbox begrenzt nur den Schaden, nicht das Verhalten.
    • Kein Schutz vor versehentlichem Push auf den falschen Branch. Der Agent darf in seinem Worktree alles — auch git push --force origin master. Klassische Maßnahmen (geschützte Branches in GitHub/GitLab, Pull-Request-Reviews) bleiben wichtig.

    Tiefen-Doku (Profil-Inhalt, Bind-Mounts, Strategie-Architektur): Features → Sandbox.

    Secrets¶

    Schlüssel Default Wofür
    webhookSecretFile null Pfad zur 0600-Datei mit dem HMAC-Secret für Webhook-Verifikation. Pflicht, wenn webhookEnabled: true.
    tokenKeychainService null macOS-Keychain-Service-Name, falls Token dort liegt.
    tokenLibsecretAttributes null Linux-libsecret-Attribute, falls Token dort liegt.

    Agent-Routing-Allowlists¶

    Schlüssel Default Wofür
    agentBackends null (Routing aus) Liste erlaubter Backends, falls Operator das Backend pro Ticket per Label überschreiben will. Sicherheitsmodell: Allowlist.
    agentModels null (Routing aus) Analog für agent:model:<wert>-Labels.

    Details: Features → Agent-Routing.

    Stufe 4 — Operativ¶

    Schalter für Beobachtbarkeit, Logging, Service-Modus:

    Logging¶

    Schlüssel Default Wofür
    logLevel "info" debug / info / warn / error.
    logFile null (= nur stdout) Pfad für rotierende Log-Datei (z. B. ~/.agentry/agentry.log).
    logMaxBytes 10_485_760 (10 MiB) Maximalgröße pro Log-Datei, bevor rotiert wird.
    logMaxFiles 5 Wie viele rotierte Dateien aufgehoben werden.

    Health- und Metrics-Endpoint¶

    Schlüssel Default Wofür
    healthEnabled true HTTP-Endpoint für /healthz, /readyz, /status, /metrics.
    healthHost "127.0.0.1" Bind-Adresse. Für externe Monitore auf 0.0.0.0 setzen — vorher Firewall prüfen!
    healthPort 8765 Port.

    Details: Features → Health-Endpoint + Metrics.

    Update-Notifier¶

    Schlüssel Default Wofür
    updateCheckEnabled true Prüft alle 24 h gegen agentry-dist, ob es neue Versionen gibt.
    updateCheckIntervalSeconds 86400 (24 h) Re-Check-Abstand.
    updateCheckRepo "torben-erz/agentry-dist" Ziel-Repo für Forks/Mirrors anpassbar.

    Details: Features → Update-Notifier.

    Typische Operator-Profile¶

    Drei häufige Setups als Vorlage — jeweils nur die Schlüssel, die vom Default abweichen:

    Profil A — Solo-Entwickler, ein Repo¶

    {
  "watch": "torben-erz/mein-projekt",
  "agentBackend": "claude-code"
}

    Das ist der einfachste sinnvolle Setup. Defaults greifen für alles andere — Polling alle 5 s, plattform-Sandbox, GitHub als Provider, Token aus gh auth token.

    Profil B — Mehrere Repos, mit Sandbox-Profil¶

    {
  "watch": {
    "type": "repos",
    "value": ["torben-erz/proj-a", "torben-erz/proj-b"]
  },
  "agentBackend": "claude-code",
  "sandbox": {
    "default": "macos-sandbox",
    "strategies": {
      "macos-sandbox": { "profile": "/etc/agentry/strenger.sb" }
    }
  }
}

    Profil C — Service-Modus mit Webhooks und File-Token¶

    {
  "watch": "torben-erz/produktiv-repo",
  "agentBackend": "claude-code",
  "tokenFile": "/etc/agentry/github.token",
  "webhookEnabled": true,
  "webhookSecretFile": "/etc/agentry/webhook.secret",
  "healthHost": "0.0.0.0",
  "logFile": "/var/log/agentry/agentry.log"
}

    Voraussetzung: Reverse-Proxy oder direkter HTTPS-Endpunkt für POST /webhook/github (siehe Webhooks), plus GitHub-Webhook im Repo angelegt (entweder via agentry webhook install oder von Hand).

    Was bewusst NICHT in der Config steht¶

    • Tokens selbst — gehören in Env, Keychain, libsecret oder eine 0600-Datei. Niemals direkt in die Config.
    • Sandbox-Profile — werden referenziert (sandbox.strategies.macos- sandbox.profile = "/etc/agentry/agent.sb"), aber liegen als separate Datei.
    • Repository-Listen für Multi-Repo via Glob — Agentry nimmt nur explizite Repo-Listen, kein Wildcard-Match. Wenn du einen ganzen Owner-Scope willst: watch: {"type": "ownerScope", "value": "owner"}.

    Validieren vor dem Restart¶

    Bei jeder Config-Änderung:

    agentry config validate

    Exit 0 = alles ok. Exit 1 = Fehler werden auf stderr ausgegeben mit Validator-Begründung. Erst danach Daemon neu starten.

    Diese Seite ist didaktisch geordnet — die alphabetische Liste mit allen Defaults und Validator-Regeln liegt in Referenz → Config.
