    FAQ — häufige Fragen¶

    Sammlung der Fragen, die regelmäßig kommen. Wenn deine Frage hier fehlt: siehe unten — wir tragen sie nach.

    Allgemein¶

    Was ist Agentry in einem Satz?¶

    Ein wartender Daemon, der GitHub-Issues mit Label agent-task autonom in Pull Requests verwandelt — und das gleiche für PR-Reviews mit Label agent-revise. Plattform-agnostisch (GitHub und GitLab), Backend- agnostisch (Claude Code oder Codex).

    Was kostet das?¶

    Während der Closed-Beta: nichts. Pricing und Modell-Mechanik (Subscription, Tier, etc.) werden nach Beta-Feedback festgelegt — siehe Stufenplan in den Vertriebsmodellen. Vorläufig beschlossener Pfad ist Open-Core + On-Prem-Subscription, was heißt: ein OSS-Kern bleibt gratis, Premium-Features (Jira-Source, SSO, Audit-Log etc.) kommen mit Subscription. Was du heute installierst, wird dir nicht hinter eine Bezahlschranke gezogen.

    Wie unterscheidet sich Agentry von Devin / Cursor Background Agent / Copilot Workspace?¶

    Achse Agentry Devin / Cursor / Copilot
    Hosting On-Prem (Daemon läuft bei dir) SaaS (Hosting bei Anbieter)
    Code-/Token-Zugriff bleibt komplett bei dir geht über fremde Server
    Quellsysteme GitHub + GitLab (heute), Jira/ServiceNow (Roadmap) meist nur GitHub
    Agent-Backend Claude Code oder Codex, austauschbar hartcodiert pro Anbieter
    Sandbox Plugin-Architektur (sandbox-exec, bwrap, …) Black-Box des Anbieters
    Lizenz/Source aktuell privat, Pfad Open-Core meist Closed-Source-SaaS

    Mehr Detail: Differenzierung.

    Wer entwickelt Agentry?¶

    Torben Daniel Erz (NanoApes). Closed-Beta läuft mit eingeladenen Testern; Source-Code ist während dieser Phase privat.

    Setup¶

    Welche Plattformen unterstützt Agentry?¶

    • macOS 14+ auf Apple Silicon (M1 oder neuer) — primäre Test- Plattform, Binary signiert + notarisiert
    • Linux (Ubuntu 22.04+, Debian 12+) auf x86_64 — wird in CI parallel zu macOS getestet

    Windows-Support steht nicht auf der Roadmap.

    Kann ich GitLab statt GitHub nutzen?¶

    Ja. Setze provider: "gitlab" in der Config und gib watch als Pfad auf ein GitLab-Projekt an. Self-hosted GitLab funktioniert via host (gleicher Schlüssel wie für GitHub Enterprise Server). Volle Liste der unterstützten Watch-Formen: GitLab-Source.

    Funktioniert das mit GitHub Enterprise Server (GHES)?¶

    Ja. Setze host in der Config auf deinen GHES-Hostnamen (ohne api.- Präfix, z. B. "github.example.com"). Agentry leitet daraus die API-URL https://github.example.com/api/v3 und die Clone-URL ab. Vorausetzung: gh auth login --hostname github.example.com einmal ausgeführt. Details: Konfigurations-Referenz → host.

    Funktioniert das mit Monorepos?¶

    Ja, solange der Agent in seinem Worktree den nötigen Kontext findet. Bei sehr großen Monorepos (mehr als ~50 k Dateien) wird das Polling und der Worktree-Setup spürbar langsamer — das ist keine harte Grenze, aber ein praktisches Limit.

    Was, wenn bubblewrap auf meinem Linux nicht im Paket-Repo ist?¶

    bubblewrap ist auf Ubuntu/Debian, Fedora, Arch und openSUSE in den Standard-Repos. Auf älteren oder spezielleren Distros: aus Source bauen (make install), oder Sandbox explizit auf "none" setzen — dann startet Agentry trotzdem, läuft aber ungesandboxed (nicht empfohlen). Default-Plattform-Sandbox ist Pflicht aus Sicherheitsgründen, siehe Sandbox.

    Daten und Sicherheit¶

    Welche Daten sehen die Agentry-Maintainer (also wir)?¶

    Bei der Standard-Konfiguration: praktisch nichts. Konkret:

    • Update-Notifier macht einen anonymen HTTP-GET gegen api.github.com/repos/torben-erz/agentry-dist/releases/latest (alle 24 h). Wir sehen die User-Agent-Zeile (agentry/<version>) — kein Token, kein Repo-Name, keine IP-Korrelation.
    • Wenn du agentry update manuell aufrufst: dasselbe.
    • Wenn du agentry diagnose | pbcopy und uns den Output schickst: alles, was darin steht. Tokens, Webhook-Secrets, Ticket-Inhalte und vollständige Pfade zu Secret-Dateien sind bewusst nicht im Diagnose-Block.

    Was wir nicht sehen: dein Code, deine Issues, deine PRs, deine Tokens, dein Repo-Name.

    Wo landet mein GitHub-Token?¶

    Lokal bei dir. Agentry liest in dieser Reihenfolge:

    1. $AGENTRY_GITHUB_TOKEN (Env-Variable)
    2. macOS-Keychain (falls tokenKeychainService gesetzt)
    3. libsecret (Linux, falls tokenLibsecretAttributes gesetzt)
    4. tokenFile (0600-Datei, falls gesetzt)
    5. gh auth token (CLI-Fallback)

    Welche Quelle aktiv ist, kannst du mit tokenSource als Compliance-Schalter erzwingen. Details: Token-Handling.

    Der Token wird nur an gh-Subprocesses durchgereicht (via Env), die Agentry selbst aufruft — er verlässt deine Maschine nie.

    Was sieht Claude / Codex von meinem Repo?¶

    Alles, was im Worktree für das jeweilige Ticket liegt — also der Inhalt deines Repos zum aktuellen Stand. Plus den Prompt mit Issue-Titel und -Body. Plus, was Claude/Codex selbst von dir in ihrem Konto sehen (das ist außerhalb von Agentry).

    Was Claude/Codex nicht sehen: dein GitHub-Token, deine .agentry/-Datei, andere Repos auf deiner Maschine — die Sandbox sperrt den Agent-Prozess auf den Worktree (und einige Build-Caches) ein.

    Funktioniert Agentry offline?¶

    Teilweise. Der Daemon selbst läuft ohne Internet, aber:

    • Das Polling braucht GitHub-API-Zugriff
    • Das Pushen braucht git-Push-Zugriff zum Remote
    • Claude Code und Codex brauchen Anthropic- bzw. OpenAI-API-Zugriff
    • Update-Notifier braucht GitHub-API-Zugriff (kann mit updateCheckEnabled: false abgestellt werden)

    Reiner Airgap-Betrieb ist also nicht das primäre Setup. Wenn du in einem Netz mit strikter Firewall arbeitest, brauchst du eine allow-list für api.github.com, dein git-Remote und den Agent- Endpoint (z. B. api.anthropic.com).

    Was ist eine Sandbox und warum hat Agentry eine?¶

    Eine Sandbox ist eine vom Betriebssystem (macOS- bzw. Linux-Kernel) erzwungene Umgebung, in der ein Programm läuft, ohne außerhalb seines erlaubten Bereichs schreiben zu können. Wenn der Agent z. B. versucht, ~/.ssh/id_rsa zu überschreiben, blockt der Kernel den Zugriff — der Agent kann den Pfad zwar sehen, aber nichts hineinschreiben.

    Warum Agentry das hat: der Agent (Claude Code, Codex, …) darf in seinem Workspace alles — Code ändern, Dateien anlegen, git-Befehle. Ohne Sandbox könnte ein versehentlicher (oder böswillig getriggerter) Befehl außerhalb des Workspaces System-Files anfassen, Credentials exfiltrieren oder dein produktives Repo direkt überschreiben. Mit Sandbox bleibt der Schreib-Zugriff auf den Workspace-Ordner und typische Build-Caches (~/.cache, ~/.npm, ~/.bun, …) begrenzt.

    Plattform-Defaults sind out-of-the-box scharf — du musst nichts setzen. Konzept-Erklärung inkl. „Was die Sandbox NICHT ist": Anwendung → Konfiguration § Sandbox.

    Wie sicher ist die Sandbox?¶

    Die Default-Plattform-Sandbox (macos-sandbox auf macOS, linux-bwrap auf Linux) gibt dem Agent-Prozess eine Filesystem- Allowlist: er darf in den Worktree, in einige Build-Caches unter $HOME und in temporäre Verzeichnisse schreiben. Außerhalb davon: Read-only oder gar nichts. Process-Isolation (PID/IPC-Namespaces auf Linux), Netz bleibt offen (für git-Push und Agent-API-Calls).

    Für stärkere Isolation (volle Container oder VMs) sind die Strategien linux-container und tart-vm als Plugin-Architektur vorgesehen — Implementierung folgt bei Kundenbedarf. Siehe Sandbox und Apple-2-VM-Limit-Diskussion.

    Nutzung¶

    Was kostet ein Ticket-Run (Claude-/Codex-API)?¶

    Variabel — hängt vom Modell, der Ticket-Komplexität und der Repo- Größe ab. Typische Werte für die heutige Claude-Code-CLI mit dem Default-Modell auf einem mittelgroßen Repo: wenige Cent bis um einen Euro pro Ticket. Bei sehr großen Refactors oder komplexen Bug-Fixes mit vielen Lese-Operationen kann es höher gehen.

    Agentry selbst verursacht keine Kosten — die Rechnung läuft direkt über deinen Anthropic- oder OpenAI-Account.

    Wie lange dauert ein typisches Ticket?¶

    • Trivial (README-Update, Doku-Lücke): unter 1 min
    • Mittel (Bug-Fix mit Test, neue Konfig-Option): 2–10 min
    • Komplex (Refactoring, mehrere Dateien): 5–20 min
    • Sehr komplex: läuft ins agentTimeoutSeconds-Limit (Default 30 min) — dann lieber in kleinere Tickets zerlegen

    Daemon-Setup-Zeit (Worktree anlegen, Sandbox starten) ist meist unter 2 Sekunden. Polling-Latenz ist 0–5 Sekunden bei Default pollInterval: 5; mit Webhooks ist es sub-Sekunde.

    Kann ich mehrere Repos parallel beobachten?¶

    Ja. Setze watch auf eine Liste:

    {
  "watch": {
    "type": "repos",
    "value": ["owner/repo-a", "owner/repo-b"]
  }
}

    Oder einen ganzen Account-Scope:

    { "watch": {"type": "ownerScope", "value": "owner"} }

    Mehr: Multi-Repo.

    Wie viele Tickets parallel bearbeitet werden, steuert maxConcurrency (Default 1 = seriell).

    Was passiert, wenn zwei Tester gleichzeitig dasselbe Issue triggern?¶

    Nichts Schlimmes. TicketQueue hat einen atomaren claim(), der das Ticket dedupliziert — der zweite Versuch sieht „bereits in Bearbeitung oder erledigt" und überspringt. Bei Webhooks zusätzlich ein Replay-Schutz über X-GitHub-Delivery-IDs.

    Wie pausiere ich den Daemon kurz, ohne zu deinstallieren?¶

    Ctrl+C im Daemon-Terminal (Vordergrund) oder launchctl unload ~/Library/LaunchAgents/com.nanoapes.agentry.plist (macOS-Service) / systemctl --user stop agentry.service (Linux). Beim Stoppen werden hängende Worktrees automatisch aufgeräumt; Tickets im Repo behalten ihr Status-Label.

    Probleme¶

    Der Agent macht zu viel — wie zähme ich ihn?¶

    In den Issue-Body schreiben: „Bitte AUSSCHLIESSLICH X ändern, keine weiteren Reformatierungen oder Whitespace-Anpassungen." Funktioniert zuverlässig. Beispiel im Use-Case README-Update.

    Der Agent versteht den Auftrag nicht — was tun?¶

    Zwei Optionen:

    1. agent-revise auf den PR setzen + Review-Kommentar mit präziser Anweisung. Der Revise-Loop iteriert auf demselben Branch.
    2. Wenn der PR komplett am Ziel vorbei ist: PR schließen, Issue um bessere Beschreibung ergänzen, agent-task neu setzen — neue Pipeline mit frischem Branch.

    Mehr zur Revise-Mechanik: PR-Review-Loop.

    Kann der Agent meine Tests laufen lassen?¶

    Ja — innerhalb der Sandbox. swift test, npm test, pytest, etc. funktionieren, sofern die nötigen Tools (Swift, Node, Python) auf dem Host installiert sind. Schreib im Issue, dass du test-getriebenes Vorgehen erwartest („zuerst failing Test, dann Fix"), dann macht der Agent das auch. Siehe Use-Case Bug-Fix mit Test.

    Mein Repo hat private Dependencies — funktioniert das?¶

    Ja, wenn der Token Lese-Zugriff auf die Dependency-Quellen hat. Bei go get, npm install, swift package resolve etc. wird der gh auth setup-git-Credential-Helper genutzt, den Agentry beim Start registriert — der Token läuft also auch für Submodul-Clones.

    Was passiert bei einem Daemon-Crash mitten in der Bearbeitung?¶

    CrashRecovery greift beim nächsten Daemon-Start:

    • Tickets mit agent:in-progress-Label bekommen agent:failed (mit Failure-Kommentar, der den Crash erwähnt)
    • Tickets mit agent:revising-Label bekommen agent:revise-failed
    • Verwaiste Worktrees in ~/.agentry/workspaces/ werden aufgeräumt

    Du kannst das Ticket dann selbst neu triggern (Label flip von agent:failed zurück zu agent-task). Detail: Crash-Recovery.

    Produkt-Zukunft¶

    Wird Agentry kostenpflichtig?¶

    Ja, teilweise. Vorläufig beschlossener Pfad ist Open-Core: ein OSS-Kern bleibt gratis, Premium-Features kommen mit Subscription. Der heutige Beta-Stand entspricht dem geplanten OSS-Kern — was du heute nutzt, bleibt verfügbar. Details: Stufenplan.

    Wird der Source-Code irgendwann öffentlich?¶

    Geplant: ja, mit Stufe 1 des Stufenplans. Auslöser: positives Beta-Feedback und Vertrauen, dass die OSS/Premium-Linie sauber gezogen ist. Aktuell ist das Source-Repo privat; die Distribution (agentry-dist, homebrew-agentry) ist öffentlich.

    Kann ich Agentry kommerziell einsetzen?¶

    In der Closed-Beta-Phase: ja, aber nicht weiterverteilen. Die binäre Distribution-Lizenz ist MIT, der Source ist proprietär. Wenn du es im Unternehmen einsetzen willst und Fragen zu kommerziellen Bedingungen hast: melde dich, dann reden wir.

    Was passiert mit der Beta-Version, wenn Stable kommt?¶

    Nichts Schlimmes. Beta-Tester behalten ihre Installation; sie können via brew update && brew upgrade agentry (oder brew install agentry@stable, falls parallele Versionen kommen) auf Stable wechseln. Eine versteckte Lizenz-Bremse, die ältere Versionen lahmlegt, ist bewusst nicht im Beta-Code drin — das wäre Vertrauens-Verbrennen.

    Was passiert mit meinen Beta-Daten?¶

    Beta-Daten gibt's bei uns keine — alles, was Agentry produziert, liegt bei dir. Wenn du uns agentry diagnose-Outputs oder Bug-Reports schickst, behalten wir die zu Diagnose-Zwecken; auf Nachfrage löschen wir sie.

    Deine Frage fehlt?¶

    Schick sie an Torben Erz — Kanal je nachdem, wie du an die Beta gekommen bist (Mail, Slack, …). Wenn die Frage allgemein ist und für andere Tester wertvoll wäre, landet sie hier auf der FAQ.
